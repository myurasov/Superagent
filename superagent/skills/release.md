# Superagent release — cut a framework version

The maintainer-facing entry point for shipping a new framework version. One
run performs **preflight gate -> bump decision -> version bump -> roadmap row
-> commit -> tag -> push -> local migrate -> log -> table**. Every rule it
applies already lives in `contracts/versioning.md` and `AGENTS.md` § "Git
commits" / § "Versioning and migrations"; this skill only sequences them.

Before any `uv` call in a new shell: `export UV_PROJECT_ENVIRONMENT="${PWD}/.venv.noSync"` from the repo root.

## 0. Preflight

1. **Location and branch.** `git rev-parse --show-toplevel` is the repo root
   (`pyproject.toml` present); `git branch --show-current` prints `master`.
   Any other branch: stop and report — releases are cut from `master` only.
2. **Remote first.** `git fetch origin`, then `git status -sb`. If `behind`
   is non-zero, `git pull --ff-only` so out-of-band remote edits (README
   touch-ups, doc fixes) ride along in this release. A non-fast-forward
   refusal stops the run; never merge or rebase autonomously.
3. **Clean tree.** `git status --porcelain` shows nothing except known local
   files (editor settings such as `.vscode/settings.json`). Unrelated dirty
   framework files: ask whether to commit them first, or stop.
4. **Green gate** — every command below exits 0; a red gate ends the run
   with the failing command's output. No tagging a red tree.
   ```bash
   uv run ruff check superagent/
   uv run pytest -q
   uv run python -m superagent.tools.validate
   uv run python -m superagent.tools.anti_patterns --strict
   uv run python -m superagent.tools.add_step_index --check
   uv run python -m superagent.tools.build_skill_manifest
   git diff --stat superagent/skills/_manifest.yaml
   uv run python -m superagent.tools.memory_routing_check
   ```
   The manifest rebuild is expected to be diff-clean apart from
   `generated_at` and rows for skills edited in this release; anything else
   means a skill edit shipped without its manifest rebuild — the rebuilt
   file is committed with the release in step 4.

## 1. Decide the bump kind

Per `contracts/versioning.md` § 1: **PATCH** = bug fix / doc / refactor with
no workspace-data effect; **MINOR** = backwards-compatible significant change
(new memory file, new field, new skill touching workspace data); **MAJOR** =
breaking workspace-data or public-API change. Rule of thumb: if a workspace
authored on the previous version would misbehave or fail validation on this
one, it is at least MINOR and a migration is required.

1. Summarize `git log <last-tag>..HEAD --oneline` in one screen and propose a
   kind. Ask with `AskQuestion` (`patch / minor / major / cancel`) unless the
   user pre-decided in this turn ("cut a patch release"); a harness without a
   question tool asks in prose and waits.
2. **MINOR / MAJOR touching workspace data REQUIRE
   `superagent/migrations/<new-version>.md`.** If absent: copy
   `superagent/migrations/_template.md` to `<new-version>.md`, fill in
   `breaking` / `revertible` / pre-flight / migrate / validate / revert per
   `contracts/versioning.md` § 3.2, then
   `uv run python -m superagent.tools.version refresh-manifest` so
   `migrations/_manifest.yaml` registers it. MINOR with no workspace-data
   effect may skip the migration (say so explicitly in the roadmap row).

## 2. Bump the version

1. Edit `pyproject.toml` `project.version` -> `X.Y.Z`.
2. `uv lock` so `uv.lock` follows (it records the project's own version; a
   stale lock fails `uv sync --locked` downstream).
3. `uv run python -m superagent.tools.version current` prints `X.Y.Z`.

## 3. Roadmap Released row

Add **one** row to `superagent/docs/roadmap.md` § Released, newest-first
(directly under the table header): `| **X.Y.Z** | <today ISO> | <summary> |`.
A long-form summary is fine and encouraged (what changed, why, root cause,
test delta, whether a migration ships) but it stays a single table row. Link
the migration as `[Migration](../migrations/X.Y.Z.md)` when one exists, or
end with "No workspace-data changes — patch, no migration."

## 4. Commit

1. Stage only release files: `pyproject.toml`, `uv.lock`,
   `superagent/docs/roadmap.md`, `superagent/migrations/X.Y.Z.md` +
   `_manifest.yaml` (when authored), `superagent/skills/_manifest.yaml` (when
   rebuilt). Never `workspace/` data.
2. Subject: `Bump version to X.Y.Z` for a PATCH; `Release Superagent X.Y.Z`
   when a migration ships. One sentence, imperative, ASCII, no body.
3. Commit through the hooks (`pre-commit` re-runs ruff; `commit-msg` blocks
   AI attribution). **Never `--no-verify`.**
4. Strip trailers per `rules/git-commits.md` § 3 (the
   `filter-branch --msg-filter` snippet over `@{u}..HEAD`), then verify with
   `git log -1 --format=%B`: subject line only, no `Made-with` /
   `Co-authored-by` / vendor names.

## 5. Tag

`git tag -a vX.Y.Z -m "Superagent X.Y.Z"` on the release commit. Refuse if
the tag already exists (a re-cut means a new PATCH, never a moved tag).

## 6. Push

Pushing is an upstream write: gate it with `AskQuestion`
(`push master + tag / push later / cancel`) unless the user pre-authorized in
this turn ("cut a release and push"). On approval:

```bash
git push origin master
git push origin vX.Y.Z
```

Plain pushes only — never `--force`, never `--force-with-lease`. If the user
asks for a GitHub release page and `gh` is available:
`gh release create vX.Y.Z --title "Superagent X.Y.Z" --notes "<roadmap summary>"`.

## 7. Migrate the local workspace

The maintainer's own `workspace/` must not lag the framework it just shipped.
Dispatch into the `migrate` skill (`superagent/skills/migrate.md`): it
applies `superagent/migrations/X.Y.Z.md` interactively when one exists, or
silently advances `workspace/.version` for a PATCH-only delta. Confirm with
`uv run python -m superagent.tools.version check` -> up-to-date.

## 8. Log

Append one row to `workspace/_memory/interaction-log.yaml` per its schema:

```yaml
- id: <new id>
  ts: <iso datetime>
  skill: release
  action: release
  from_version: <previous>
  to_version: X.Y.Z
  bump: patch | minor | major
  migration: migrations/X.Y.Z.md | null
  tag: vX.Y.Z
  pushed: true | false
  summary: "<one line>"
```

No `context.yaml.last_runs` entry — releases are event-shaped, not a cadence.

## 9. Report

End with the release table:

| Field | Value |
|---|---|
| Version | `<previous>` -> `X.Y.Z` (`<bump kind>`) |
| Commit | `<sha> <subject>` |
| Tag | `vX.Y.Z` (pushed: yes / no) |
| Migration | `migrations/X.Y.Z.md` or none |
| Gate | ruff / pytest (`N passed`) / validate / anti-patterns / step-index / manifest / memory-routing — all green |
| Workspace | `.version` now `X.Y.Z` |
| Changes | `git log <prev-tag>..vX.Y.Z --oneline` (one line per commit) |

## What this skill never does

- **No `--no-verify`** on commit — the hooks are the enforcement floor.
- **No force push**, no tag moves, no history rewrite beyond the trailer strip on unpushed commits.
- **No tagging a red tree** — a failing gate ends the run before any bump.
- **No `workspace/` data in commits** — release files only.
- **No autonomous merge or rebase** — remote drift is `--ff-only` or stop.
- **No push without a same-turn confirmation** or pre-authorization.
- **No hand-edited `workspace/.version`** — that is the `migrate` skill's job.
