# Superagent add-agent skill

An agent is a role that runs skills (`contracts/agents.md`). This skill creates one of two things:

- **A project agent** — an instance of the generic `project` role for one Project. It exists through a row in `_memory/agents.yaml`; no file is written.
- **A custom agent** — a new role in the overlay, `workspace/_custom/agents/<name>.agent.md`, with its dev twin beside it.

A new **framework** role (generic, committed under `superagent/agents/`) is not made here: that is a framework change (`rules/framework-changes.md`).

## 1. Which kind

- The request names a Project ("an agent for the kitchen renovation") → § 2.
- The request describes standing work with no Project ("an agent that watches the garden") → § 3.
- Unclear → ask which, in one question.

## 2. A project agent

1. The Project must exist: find its row in `_memory/projects-index.yaml`. Its slug is the agent's slug. With no such Project, run `add-project` first.
2. Create the row (it starts `off`, with no wake):

   ```bash
   uv run python -m superagent.tools.agents set project:<slug>
   ```

3. Show the result: `uv run python -m superagent.tools.agents list` names the agent with its id and its dev twin.
4. A project agent is idle by default and wakes on a message. Offer a periodic wake only when the owner asked for one ("check the permit every day until March"), and then go through § 4.
5. Go to § 5.

## 3. A custom agent

### 3.1 The charter

Collect all of this before writing any file. Ask in one batch; propose a value for whatever the request already implies.

| Field | What to settle |
|---|---|
| Name | `^[a-z][a-z0-9-]{0,30}$`. It differs from every framework role (`uv run python -m superagent.tools.agents list`): a same-named file in the overlay would be an overlay on that role, never a new one. Reserved: `dev`, `owner`, `autocode`, `me`. |
| Purpose | One or two lines: what it is for and where it stops. |
| Skills | The skill stems it runs (framework or `workspace/_custom/skills/`). It stays inside this list. |
| Owns | The workspace paths it is the main writer of. May be empty. |
| Authority | `act`, `approve`, `prepare` or `owner` (`contracts/autonomy.md` § 2): the loosest tier it may use. |
| Duties | For each: an id, the skill, the tier, when it runs, and the check that says whether it is due. |
| Model tier | `runner` (the default for an agent that does work). |
| Cost cap | A daily cap in USD, or none. |
| Wakes | For each periodic wake it should have: the trigger with its end, the duty it serves, the expected cost per run. |

A duty's check is `cadence` (due by its stamp against a key of `config.preferences.cadences`), `none` (on request only), or the role's own script, `tool:<name>` (§ 3.3).

### 3.2 The files

Destination: `workspace/_custom/agents/` (announce it: a custom role carries workspace-specific content by design, `contracts/framework-artifacts.md`).

1. Copy `superagent/templates/agents/agent.md` to `workspace/_custom/agents/<name>.agent.md` and `superagent/templates/agents/agent.dev.md` to `<name>.agent.dev.md`. A same-named template under `workspace/_custom/templates/agents/` wins; announce it.
2. Fill the frontmatter from the charter and write the body: purpose, what it does, boundaries, duties, hand-offs. Delete the author-guide comment.
3. Fill the dev twin: design notes, the wake and check design, cost targets, how to test, a first changelog line.

### 3.3 A check script (only for `check: tool:<name>`)

Write `workspace/_custom/tools/<name>.py`. The contract:

- It is run as `<python> <script> --workspace <workspace path>`.
- **Exit 0** means due, and what it prints is the reason shown to the agent. **Exit 1** means not due. Any other exit is a failure, reported as one.
- It reads local files only and writes nothing. It costs no model call: that is its whole point.
- It finishes in seconds (it is stopped after two minutes).

### 3.4 Validate

```bash
uv run python -m superagent.tools.agents list                      # a problem with the role is named on stderr
uv run python -m superagent.tools.agents duties --agent <name>
uv run python -m superagent.tools.agents check <name> <duty>; echo $?   # 0 due, 1 not due, 3 the check failed
```

Fix what `list` names before going on. Then create the row, with the cap when the charter has one:

```bash
uv run python -m superagent.tools.agents set <name> [--daily-usd <N>]
```

## 4. Wakes: the owner approves the exact terms

A periodic wake is a grant (`contracts/agents.md` § 8). For each wake the charter names:

1. Show the terms in one block: the agent, the wake's name, the trigger with its end (`every 1d until 2027-03-01`), the check that runs first, the purpose, the expected cost per run.
2. Get the owner's yes to those exact terms. A changed term is a new question.
3. Record it:

   ```bash
   uv run python -m superagent.tools.agents grant <agent> --wake <name> --trigger "<trigger>" \
     --purpose "<why>" --approval "<the owner's words>" [--duty <duty>] [--cost <usd>] [--ends <date>]
   ```

   The tool prints the check line the wake will run first.

Never write a grant the owner did not approve, and never approve one on the owner's behalf. A run with nobody present queues the question (`uv run python -m superagent.tools.asks add --agent superagent --tier approve ...`) and creates the agent without the wake.

## 5. Offer to start

- **Agents run as sessions of their own** (`config.preferences.autocode.enabled` is true): offer `uv run python -m superagent.tools.autocode start <agent>`, per the `agents` skill. Start it only on the owner's yes: a running agent costs money.
- **Otherwise**: say how to use it now: "act as <name>" or "work on <project>" loads the role in the chat session (`agents` skill).
