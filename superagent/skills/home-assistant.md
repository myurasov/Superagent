## Step 0 — Why this exists

This skill is Superagent's HA layer: one discipline for inspecting, configuring, automating, and diagnosing ANY
install type from any harness, with no MCP dependency — plain HTTP/WebSocket calls from short scripts are far cheaper
in context than MCP tool round-trips, and the instance model (Step 10) answers most questions with zero host access.
Canonical invocation:

```bash
uv run --no-project --with requests,websockets python ~/.superagent/tmp/<script>.py
```

One-time per instance: register it per Step 1 (a missing credentials file tells you it is unregistered).

## Step 1 — Instances, credentials, and access layers

Each instance is registered in `workspace/_memory/sensitive/home-assistant-<instance>.yaml` (mode `600`, per
`contracts/sensitive-tier.md`): `base_url`, `token` (long-lived access token), optional `ssh:` (host, user, config_dir,
container) and `mqtt:` (broker host, credentials ref) sub-blocks. **Never print, echo, or commit its values** —
scripts receive credentials via environment variables at invocation time, never inline.

- **Use a dedicated admin service account for agent work**, never the owner's — tokens and actions stay separable
  and revocable. Creating it and minting its token are upstream writes: authorization first (Step 2). Headless
  minting: drive the login flow at `/auth/login_flow` to obtain an auth code, exchange it at `/auth/token` for a
  short-lived access token (+ refresh token), then WS `auth/long_lived_access_token` (up to 3650 days). Offline
  fallback (HA stopped): edit BOTH `.storage/auth` (user + credential + refresh_token records) and
  `.storage/auth_provider.homeassistant` (password hashes, base64-encoded bcrypt); clone an existing record's JSON
  shape in each.
- **Access layers, in preference order** (`contracts/local-first-read-order.md`): 1. the local instance model
  (Step 10) for anything not live; 2. REST (`/api/states`, `/api/history/period`, `/api/config/...`);
  3. WebSocket (token auth → `recorder/statistics_during_period`, `config_entries/*`, registry commands,
  `lovelace/*`, `energy/*`); 4. config-file edits over SSH; 5. container/host ops (Step 9).
- **Full coverage:** the token sees live state and, via WS registry commands (`config/entity_registry/list`,
  `config/device_registry/list`, `config_entries/get`), disabled rows too; only the `deleted_*` tombstones and some
  internals exist solely in `.storage/` — so API and raw-registry counts can differ; normal. **APIs drift
  across core versions:** a REST endpoint that 405s after an update usually has a WS equivalent (e.g. config-flow
  progress moved to WS `config_entries/flow/progress`) — look before assuming breakage.

## Step 2 — Upstream-write discipline: read-only by default

**Every state-changing call to HA or any device behind it is an upstream write** (`AGENTS.md` Non-Negotiable 6; `contracts/privacy.md`): service calls that actuate hardware, automation and config edits, registry changes, restarts.

- **Reads need no gate. Writes are per-call authorized**, loudly declared before the call ("this switches the
  heater off") and logged to `interaction-log.yaml` (§ Logging). A standing task authorizes its stated scope only.
- **Never modify, reset, or reflash a physical device without explicit confirmation.** Before wiring ANY device
  HTTP/MQTT endpoint into an automation or button, verify its semantics from firmware docs/source — a parameter
  named `reset` may be a FACTORY reset while `reboot` is the warm restart. Exercise destructive-looking endpoints
  manually on one unit first, name the HA command after the verified behavior, confirmation dialog on irreversible buttons.
- **Firmware flashing** additionally requires a kept per-unit stock-firmware dump, checksums verified against
  published sums, a proven restore path, and a module-dependency check — flashing only the application image onto
  too-old system firmware/bootloader boot-loops the device; flash the parts in the documented order.
- **Never touch vendor-cloud accounts** (create, reconfigure, delete) — always the user's own act.

## Step 3 — Config-change discipline: packages, check_config, reload vs restart

**All agent-authored YAML goes in `packages/`** (`homeassistant: packages: !include_dir_named packages`), one file
per device or subsystem — **NEVER appended to `configuration.yaml`**: any tool that rewrites that file (e.g.
truncating from a marker to EOF) silently wipes appended blocks, and because YAML entities keep running on cached
runtime config, the loss surfaces only at the NEXT restart — days later, far from the cause. **Gated deploy for every
YAML change:** timestamped backup of the files touched → write → `check_config` as a gate with automatic revert on
failure → restart/reload only on a clean check → verify in the registries and `/api/states`. Never restart onto an
unchecked config — broken YAML takes down unrelated integrations too.

| Change | Cheapest safe action |
|---|---|
| Automation add / edit / delete | REST `POST`/`DELETE` `/api/config/automation/config/<id>` — HA persists to `automations.yaml` and reloads itself; no file surgery, no restart. Requires the `config` integration and UI-managed automations (`automation: !include automations.yaml`) — verify both on this instance first. Automations defined in `packages/` are edited in their file + `automation.reload` (reloads all YAML automations), not via this endpoint. |
| Template edits (incl. under `packages/`) | `template.reload` — works once the `template` domain is loaded. |
| FIRST `template:` block (any new top-level domain) | Full restart — `template.reload` returns 400 (domain not loaded); `homeassistant.reload_all` silently does nothing. |
| `filter` / other classic-platform sensor changes | Restart. |
| One integration stale or frozen | REST `POST /api/config/config_entries/entry/<id>/reload` — first-line fix for a dead push connection. |
| Pause an integration, keep its config | WS `config_entries/disable`; re-enable the same way. |
| `.storage/` registry surgery | HA STOPPED, single stop → edit → start pass. |

- **After a restart**, a state-based template sensor can stick at `unknown` when its sources were not yet initialized
  at startup and update rarely — kick with `homeassistant.update_entity`, or make it trigger-based with an HA-start
  trigger (trigger-based templates restore state but cannot be force-evaluated).
- **`.storage/` rules:** never grep the JSON — a zero grep count can hide hundreds of matching entities; parse and
  query structurally. Edit only while HA is stopped (it rewrites these files on shutdown, clobbering live edits),
  from idempotent scripts. Registry saves are debounced — re-pull before concluding a write failed.
- **Disable, don't clobber:** stamp `disabled_by` only on rows currently null — overwriting `integration` silently
  re-enables those rows later. Pattern: entry `disabled_by: user`, cascaded rows `disabled_by: config_entry`; UI
  re-enable clears them. When merging automations, keep the survivor's `id` (it inherits the registry row —
  entity_id, name, history) and purge the retired twin's row while stopped. Removing a config entry tombstones its
  orphans into `deleted_*` on next start; API deletion may return `require_restart: true`.
- **Restarts and reloads must never register as real-world events:** gate power-restore automations against HA startup
  with minimum-interval guards; build accumulators (Step 4) so a reload mathematically cannot add to a total —
  restart transients are the biggest source of phantom actions and phantom consumption.

## Step 4 — Automations and template sensors

- **Trigger on entity ids, never device ids** — re-pairing hardware orphans device-id triggers and the automation
  silently stops firing; entity ids transplant across hardware. Automations created from a device page use device
  triggers: convert them. Replace `time_pattern` polling with a state trigger plus `for:` — precise, cheaper, self-documenting.
- **"B follows A" coupling:** one template binary sensor + one automation (`mode: restart`, trigger ids, a `choose:`
  block) — not separate on/off automations that drift apart; `mode: restart` also stops flap-stacked runs. Keep
  closed-loop control (reading → actuator) in HA automations, not device firmware — editable, traceable, disableable.
- **For some integrations (notably network-controlled TVs), `remote.*` reflects connectivity, not power** — `on` in standby, flipping on reconnect; verify per integration. Model "device is on" over the `media_player` state (not in off/standby/unavailable/unknown) with a short `delay_off`.
- **Presence from `zone.home` occupant count:** leaving = 0 sustained (debounce); arriving = 0 → >0; an
  `input_boolean` guest mode pauses both. Add conditions (dark-only, empty-house-only) deliberately, and before
  rewriting ANY automation enumerate every behavior the old one provided and consciously keep or drop each — a
  dropped side behavior surfaces days later as "the light stopped following the door".
- **"Automation X stopped working":** verify it ever existed — the behavior may have been a side effect of a
  different, since-rewritten automation; recorder history of the trigger entity plus current configs is ground
  truth, and concurrent edits get audited for side effects. Sweep periodically for dead automations (trigger
  entities removed) and orphaned `automation.*` rows; verify "near-duplicates" watch the same source before merging.
- **Build the alerting layer** — the commonest gap is many contact/motion/leak/presence sensors and zero notify
  automations (door open at night/away, battery digest, thresholds); one current `mobile_app` target suffices, and
  stale registrations from retired phones get pruned — dead entities, corrupted presence logic.

Template-sensor traps — these corrupt data silently:

| Trap | Rule |
|---|---|
| Unit-conversion readback | For sensors whose device_class has unit-system conversions (temperature, volume/gas/water, pressure, speed, ...), HA converts the state to the configured unit system (imperial OR metric); reading `this.state` — or another sensor's state — back into math tuned for the native unit silently corrupts it (°C stored back as °F, litres as ft³). Keep every value that carries across updates — totals, EMAs, watermarks — in ATTRIBUTES (stored verbatim, never converted) in one fixed unit; render the state from the attribute. |
| Unguarded accumulators | Give every `total_increasing` accumulator a version-tag attribute (e.g. `basis: "v2"`) naming what the watermark was recorded against; on mismatch, re-base (and reset if appropriate) WITHOUT accumulating — redefining a source sensor must never book as consumption. Bump the tag on every redefinition. |
| Neutral fallbacks | Never let a correction factor default to `\| float(1)` (or a believable `\| float(0)`) while inputs are unseeded: across a reload, corrected sensors transiently equal uncorrected ones and downstream counters book the settle-back as phantom usage. Declare the sensor unavailable via an `availability:` template until inputs exist and chain `has_value()` up every derived sensor — unavailability freezes an accumulator harmlessly; a plausible fallback corrupts it. |
| Unconditioned inputs | Condition noisy sources BEFORE any math sees them: `filter` platform `outlier` (window + radius) then `time_simple_moving_average` — filtering downstream of derived math is too late. Clamp inputs to their physical domain before `acos`/`sqrt` (`{% set h = [[x, hi] \| min, lo] \| max %}`) or one bad reading cascades NaN through every derived sensor. Quantize a derived level to steps above its residual jitter before it drives an accumulator. |
| Smoothing / debounce | Pure-YAML EMA: trigger-based sensor on a fixed `time_pattern` tick, `ema = prev + alpha * (raw - prev)`, `alpha = 1 - exp(-tick_seconds/tau_seconds)`; handle three seed cases explicitly (both none → none; raw missing → hold prev; prev missing → seed with raw); high-precision value in an attribute, rounded copy as state. Composite binary sensors carry availability guards on sources plus `delay_off` so dropouts do not flap automations. |

## Step 5 — Evidence: history, statistics, and the recorder

| Task | Rule |
|---|---|
| Raw history | `GET /api/history/period/<start>` WITHOUT `end_time` returns ONE day — multi-day queries silently truncate and can look like the recorder died mid-window. Always pass `end_time`. |
| Trends | Prefer WS `recorder/statistics_during_period` — hourly long-term statistics (never purged) for long windows, with `period=hour/day/week/month`; 5-minute short-term statistics exist only inside the recorder purge window (default 10 days). Statistics compile on a 5-minute cadence, so a new sensor has none (`energy/validate` reports `statistics_not_defined`) until the first window passes; not an error. |
| Baseline | Before any change, snapshot config-entry/device/entity/automation counts and current log ERRORs so verification separates new failures from pre-existing ones and confirms counts moved exactly as expected. Validate every sensor change empirically, before/after, against recorded data. |
| Ground truth | Validate derived metrics against a window of known near-zero usage — it exposes temperature breathing, restart transients, and accumulator bugs no code review finds. |
| Recorder diet | Measure first — a handful of diagnostic sensors commonly produce ~90% of all rows; default retention times a large entity population makes a multi-GB database. Exclude noisy raw sensors via `recorder:`, point graphs at throttled `filter` copies, set a deliberate `purge_keep_days`, lean on hourly long-term statistics for year-scale trends (they survive purges), reclaim with `recorder.purge` (`repack: true`) + `recorder.purge_entities` in a quiet window. |

## Step 6 — Dashboards and energy

| Topic | Rule |
|---|---|
| WS dashboards | Storage-mode dashboards: `lovelace/dashboards/create` then `lovelace/config/save`. The `url_path` MUST contain a hyphen or creation fails. |
| Energy cards | Outside the built-in Energy panel they need an `energy-date-selection` card in the same view or they render no data. The built-in panel's electricity/gas tabs are fixed — a custom view of energy + gauge/entities cards puts everything on one page; hide the built-in panel per-user via sidebar edit. |
| Energy prefs | Version-dependent schema (WS `energy/*`): fetch current prefs and mirror their shape — grid sources have flattened across versions while still requiring fields like `cost_adjustment_day`; gas/water `stat_rate` demands a VOLUME_FLOW_RATE device class. Never feed `stat_rate` a noisy derivative of a quantized level sensor — skip it. Validate after save; iterate until `energy/validate` is clean. |
| Gas units | Gas sources accept volume units (L, m³, ft³, CCF, MCF) or energy units (Wh/kWh/MJ/GJ...) — never gallons. Pick the accumulator's `unit_of_measurement` from those lists up front and convert explicitly with a fixed constant in the template; the frontend then displays per the configured unit system (a native-litre sensor renders as ft³ under US units) — display conversion, not a data problem. |
| Level → consumption | High-watermark + hysteresis accumulator (Step 4 traps apply): accumulate only on a net drop above a noise-sized threshold; a rise above a larger threshold is a refill that re-bases without accumulating; cap the plausible per-update drop; anything between touches nothing. A bare decrease-only counter double-counts oscillation as usage. |
| Tank temperature | Liquid-fuel tank levels breathe with temperature — real thermal expansion (liquid propane ≈ 0.3%/°C) — so an uncorrected feed books weather as consumption. Correct to standard reference-temperature volume with published saturated-liquid density physics (the compensation fuel-delivery meters apply), never a statistical fit to a short window: a "better-scoring" fit encodes real usage into its coefficients, then eats consumption on cold days. The sensor's reported temperature is often its electronics die, not the liquid bulk — verify by comparing it against ambient air before trusting it as medium temperature; if it tracks air, estimate bulk temperature as an hours-scale EMA of the die reading and validate the time constant against recorded history. Keep raw sensors untouched; publish `*_corrected` variants alongside, point accumulators and Energy at the corrected feed, and show both so divergence stays visible. |
| Smart plugs | Multi-outlet plugs may switch outlets individually while every port reports identical combined totals — use only ONE duplicate set in energy totals or they double-count; isolate one device by switching the other port off. Cloud-polled plug sensors can lag by minutes. Quantifying standby loads often justifies a "peripherals follow the display" automation. |

## Step 7 — Integrations, devices, MQTT, and commissioning

| Area | Rules |
|---|---|
| Config flows | Fully drivable over the API — add, reconfigure, delete entries without the UI (REST flow steps: handler + user step; progress via WS on newer cores); registry updates also work over WS. |
| Installed ≠ configured | The startup warning "custom integration ... has not been tested" fires for every folder under `custom_components/` (disk-scan artifact), and config-entry setup emits ZERO log lines at default WARNING level — absence of errors proves nothing. Liveness = config entries + devices + entities for the domain; zeros across all three is dead code. Unconfigured components are intent, not capability. |
| Dependencies | Resolve under HA core's `package_constraints.txt`: pinning above the constraint fails with "Requirements for <domain> not found"; a constraint-free `pip --dry-run` falsely reports OK — test against HA's constraint file. `pip install --no-deps` in the container is a stopgap that dies on recreation. |
| Local patches | Any shim to a custom component's source is silently wiped by its next update — keep it as a re-runnable script plus a `.orig` backup, recorded in the instance model with its removal condition; every component update is a re-patch event. Components on unofficial vendor-cloud APIs are brittle — document the exact re-auth procedure the day it first works. (SSO-only vendor logins: OAuth tokens are sometimes extractable from the vendor web app's browser storage — check IndexedDB as well as localStorage — but SSO tokens carry claims password logins never produce and can crash untested auth-library paths.) |
| Cloud → local migration | Migrate BEFORE the core update that kills the custom — deprecation warnings ("will stop working in Core 20xx.x") predict exactly which break. Transplant identities: match devices by stable vendor id, copy entity_ids/names/areas onto the new rows so history, automations, and dashboards survive; verify a control round-trip before deleting the old entry (many devices need a per-device "LAN control" toggle in the vendor app first). Local control also cures cloud-induced `unavailable` churn. |
| HACS removal | Three places, HA stopped: in `.storage/hacs.data` AND `.storage/hacs.repositories` set `installed: false` and drop `installed_commit`/`version_installed` — both are full catalogs where "not installed" is the correct resting state; never delete records. Purge the HACS tracker device and its entities from the registries, then delete `custom_components/<domain>/` — never only the folder. Storage layout and the per-repo device/entity set vary by HACS version — inspect the installed version's `.storage` records before editing; when a browser is available the HACS UI removal is equivalent and version-proof (preferred). Its per-repo device + update entity are bookkeeping, not hardware. |
| Push zombies | The connection dies when the device sleeps, the entity stays available with a frozen state, and each entry reload reads one fresh snapshot then goes deaf again. After ANY restart, verify push states actually MOVE; a labelled `time_pattern` entry-reload automation is a legitimate stopgap until a core/library update fixes the root cause — then remove it. Cloud/MQTT-backed devices can take ~30 minutes of session settling after reconfiguration — re-check later before diagnosing failure. |
| MQTT | Verify layer by layer before touching config: broker up, device publishing (`mosquitto_sub` on its topic), HA `mqtt` entry loaded. Set `expire_after` (a small multiple of the publish period) so a dead device goes unavailable instead of feeding stale values downstream. Decide a per-unit topic-prefix scheme (`<base>/<unit>/`, named by location/role, never serial) before the first of several identical devices. Harden the broker day one: no anonymous access, a user per client class, restrictive password-file permissions, credentials in a secrets store. The broker connection is a UI config entry while MQTT entities may live in YAML packages — know which layer owns what. Replacement MQTT firmware + a local broker (+ `rest_command` for verified HTTP actions) is the durable escape hatch when a vendor cloud dies. |
| Matter commissioning | On HA OS use the official Matter Server add-on (config flow auto-discovers it). On Container, run it as a sibling container (host network, `/run/dbus` read-only, explicit bluetooth adapter) and add via config flow at `ws://<host>:5580/ws` — `127.0.0.1` only when HA shares the host network. A `commission_with_code` BLE scan timeout means the device is NOT advertising — prove the adapter with `bluetoothctl` on the host first; many devices do not re-arm pairing on a power cycle and need a vendor factory-reset sequence (the user performs the physical steps). If HA's `bluetooth` integration shares the commissioning adapter, disable that config entry for the duration (adapter contention can kill attestation mid-handshake); re-enable after. A light behind a dumb wall switch: set `power_on_behavior: ON`; `unavailable` while the switch cuts power is expected, not a fault. |
| BLE reality | Identify unknown beacons by ASCII-decoding the UUID and the MAC OUI; a house adapter hears past walls, and an integration's device list is "ever seen", not "present now". Generic beacon trackers double-track devices, never forget, and pour strangers' devices into the recorder — disable unless dedicated iBeacon fobs are in use. Crowd-located item tags rotate their advertised key (~15 min, anti-stalking), so no local integration can identify one; for presence use an iBeacon fob with BLE proxies or an event-accurate physical sensor. |

## Step 8 — Diagnostics playbook

Entity `unavailable`/`unknown` — walk the chain outward-in, verifying each layer before blaming the next:

1. **Device alive and powered?** Ping / its own web page / broker traffic. A device behind a wall switch or a
   switched plug port is unavailable whenever upstream power is off — expected, not a fault.
2. **Transport up?** Broker container, LAN reachability, host networking + D-Bus for BLE (Step 9).
3. **Integration entry loaded?** Check config entries via the API; try an entry reload.
4. **Config gone from disk?** Parse/grep the config dir; diff on-disk YAML against what you believe you wrote and
   the model's `raw/` mirror (Step 10) — a wiped block surfaces only at the next restart, long after the loss.
5. **Restart-stranded template sensor?** `homeassistant.update_entity` (Step 3).
6. **THEN read logs** (`docker logs` on Container; `ha core logs` on HA OS/Supervised; `home-assistant.log` in the
   config dir everywhere). Add `logger:` filters for chatty module paths — hundreds of warnings an hour drown real failures.

Verify the evidence supports an action before restarting or changing state; ship multi-command SSH work as script files, never fragile quoted one-liners. Known traps:

| Symptom | Reality |
|---|---|
| `check_config`: "Device ... has no config entry from domain <x>" | False positive on device triggers — the checker runs without config entries; trust the exit code and the real boot log. The SAME message for a freshly re-paired device IS real evidence of a silently orphaned trigger (Step 4). |
| Hardware-looking fault on a reflashed / long-lived device | Rule out corrupted persisted state (EEPROM/NVS surviving firmware swaps) with a factory reset + clean re-setup before patching firmware — and distinguish "working in a different mode (setup screen)" from "recovered". |
| Implausible "temperature" | Often the electronics die, not the medium being measured (Step 6). |
| GitHub API rate-limited | Read the latest release tag from the `/releases/latest` redirect `Location` header — no auth needed. |

## Step 9 — Container and host ops (self-hosted)

Detect the install type FIRST — every host operation dispatches on it:

| Operation | HA OS / Supervised | Container | Core (venv) |
|---|---|---|---|
| Core update | `ha core update` / Settings → System → Update | `docker pull` pinned tag + recreate | `pip install --upgrade homeassistant` inside the venv |
| Config check | `ha core check` | `check_config` inside the container | `hass --script check_config` in the venv |
| Logs | `ha core logs` | `docker logs` | `home-assistant.log` in the config dir (present everywhere) |
| Backup | built-in Supervisor backups | full config-dir copy (row below) | config-dir copy |
| MQTT / Matter services | official add-ons | sibling containers | host-installed services |
| Shell access | SSH add-on / Samba into `/config` (host shell only via developer SSH, port 22222) | SSH to host + `docker exec` | local shell as the HA user |

The rest of this step is the Container path:

| Topic | Rules |
|---|---|
| Install type | A Container install (plain Docker) has no Supervisor: no `ha` CLI, no add-ons, observer port closed — anything an add-on would provide (MQTT broker, Matter server) runs as a sibling container, and updates are `docker pull` + recreation. |
| Image pinning | Pin to an explicit version tag — never `:latest`/`:stable` (frozen at pull time: the running version can be a year behind while the tag looks current). Compare running version to the latest release; keep the previous image for instant rollback — updates become deliberate tag changes, not surprise pulls. |
| Core update | Preflight disk space → capture the exact container recipe from `docker inspect` (network mode, privileged, config + D-Bus mounts, TZ) → snapshot counts and log ERRORs (Step 5) → stop → full config-dir backup INCLUDING the recorder DB and any root-owned files (common when the container runs as root; user-level rsync fails on those, exit 23 — copy via a temporary root container mounting both dirs) → recreate on the pinned new tag. Expect the API up within minutes with DB schema migration continuing in the background — do not panic-restart. Afterwards diff entry failures against the baseline, retest known defects, retire workarounds the update obsoleted. |
| Networking | LAN discovery (UDP multicast/SSDP) and Bluetooth require host networking with `/run/dbus` mounted — verify `NetworkMode=host` and the mount in `docker inspect` before relying on any LAN or BLE integration. |
| Scripts and pip | `docker exec <c> python3 - <<EOF` silently no-ops — docker forwards no stdin without `-i`. Ship scripts as files (scp to host, `docker cp` in, `docker exec` the file), which also dodges heredoc-quoting traps. Any `pip install` inside the container dies on recreation — record it as a shim with its removal condition, never as a fix. |
| Backups | Backups on the same disk are not backups — the box dying takes them along. Shrink the recorder DB first (it dominates backup size), copy off-box on a schedule, and verify retention count and file ownership actually permit a restore. |

## Step 10 — Instance knowledge: `ha-model/` and `home-assistant.<instance>`

Two durable stores keep host access rare. **The instance model** lives at
`Domains/<domain>/Resources/ha-model/` (typically the home domain — run
`uv run python -m superagent.tools.domains ensure <id>` first):

- `overview.md` — install facts (type, core version + image tag, update dates with backup locations, retained image
  ids, what each update fixed AS WELL AS broke), counts, device stack, automation patterns, an index of the model
  files. Stamp every snapshot date; mark spot-updates explicitly ("counts below predate the update").
- Greppable inventories — config entries (domain/title/disabled, auth stripped), devices by area with
  manufacturer/model/integration, entities as CSV rows, an automation index (triggers/conditions/services) —
  answering "what do we have", "what watches this entity", "how much is disabled cruft" with zero host access.
- A custom-component register — per component: version, install channel, live-vs-inert as verified entry/device/entity
  counts with verification date, LOCAL PATCHES with backup filenames and re-apply pointers, re-auth procedures.
  Unconfigured components are marked intent-not-capability.
- `health.md` — dated, ranked findings and backlog; strike fixed items recording the date, backup path, and the
  script/task folder that did the work; promote every incident into a reusable recipe.
- `raw/` — scrubbed verbatim mirror of every agent-managed config file. Diffing it against the live host reveals
  drift and out-of-band edits; after an accidental wipe it is the restore source. **Update it IN THE SAME TURN as
  any instance change** (Step 10a).

Refresh via a two-stage pipeline: a read-only collector stages UNREDACTED pulls (config, `.storage`, component
manifests, sizes, log tail, container facts) into machine-local scratch under `~/.superagent/tmp/` — never the repo —
and a distiller writes only scrubbed files (tokens, passwords, coordinates redacted) into the model. Collector path
per install type: SSH add-on or Samba into `/config` on HA OS/Supervised; SSH to the host, plus `docker exec` for any
root-owned files (e.g. when the container runs as root), on Container; direct file reads on Core.

**The per-instance skill — `workspace/_custom/skills/home-assistant.<instance>.md`:**

1. **Before working on any specific instance**, check `workspace/_custom/skills/` for
   `home-assistant.<instance>.md`. If it exists, follow it on top of this skill.
2. **If it does not exist, create it at the first successful session** — following the Naming-and-shape spine
   below — capturing the credentials-file pointer, install type, access
   shapes that worked, and pitfalls. Do not wait for it to "look recurring": the first session is when the knowledge is fresh.
3. **One file per instance — never mix.** A second instance's quirks in the first's file hands the next session
   wrong hosts, wrong entity ids, wrong procedures. On finding mixed content, split immediately, same turn: move
   the foreign content to its own file, leave a one-line pointer behind, note both Changelogs.
4. **Maintain it live — see Step 10a.** These files name the user's hosts, entities, and devices, so they live in
   `workspace/_custom/skills/` — NEVER under `superagent/` (Framework Artifact Creation Contract); that is exactly
   why THIS file stays free of any specific setup.
5. Never store credentials in it — reference the password manager (`vault_ref`) or the `_memory/sensitive/` file and rely on the persisted token.

**Naming and shape are deliberately portable:**

- **Filename**: `home-assistant.<instance>.md` (dot-separated, in a flat skills directory).
- **Frontmatter**: `name: home-assistant.<instance>`, `description` (folded `>-`), `triggers`,
  `mcp_required: []`, `mcp_optional: []`, plus `extends: superagent-home-assistant` and optional instance keys
  (`credentials_ref`, `install_type`) — extra keys are ignored by other hosts.
- **Section spine**: *When to Use → Connection and Session → numbered procedure steps → Capture → Verification →
  Guardrails → Pitfalls Log → Changelog*.

## Step 10a — Live maintenance: update instance knowledge IN THE SAME TURN

**A per-instance skill is a live logbook, not a write-once document** — and the `ha-model/` mirror is only
trustworthy while it moves with the instance. The only cheap moment to record a lesson is the moment it is learned; a
session that hits a quirk and does not write it down guarantees the next session pays the same debt.

**Trigger — the moment ANY of these happens, stop and update the files before the turn ends:**

- a documented endpoint, entity id, path, or flow **no longer works** (core update, re-pair);
- a command **fails in a way the skill did not predict** (405 drift, schema change, debounce race);
- you find a **better path** (a WS command replacing an SSH round-trip, a cheaper verification);
- you learn a **new constraint** (settling time, rate limit, root-owned file, unit quirk) or the **auth shape
  changes** (token rotated, SSH key moved, broker credentials changed);
- you discover a **category the instance is bad at**, so future sessions route around it;
- **any agent-managed config file changes** → refresh the `raw/` mirror and touched inventories.

**How to record it** — append a dated bullet (`YYYY-MM-DD`) to `## Pitfalls Log`; if the change alters a documented
procedure, edit that procedure in place too. `## Changelog` line only for substantial revisions. **Also capture the
signal** to `_memory/action-signals.yaml` same-turn (`kind: artifact-critique` or `correction`) per
`contracts/capture.md` § 7.2a — the instance skill records the HA knowledge; the signal records the framework friction.

**Write the pitfall so it prevents the failure, not so it narrates it** — symptom first, then cause, then fix:
"entities frozen after restart but the device pings — the push integration zombied; reload the entry, then verify
states MOVE" saves the next session; "integration acted weird" saves nobody.

**This is not optional and not deferrable to a cleanup pass.** It is `AGENTS.md` § "Knowledge discipline" — retention
is opportunistic — applied to instance knowledge. If a session ends with new knowledge and an unchanged skill file (or
a stale `raw/` mirror), that is a defect.

## Step 11 — Hard rules and known constraints

1. **Read-only by default; every upstream write is per-call authorized and logged** — service calls, config
   edits, registry changes, restarts, and every physical device behind HA (`contracts/privacy.md`).
2. **Never restart onto an unchecked config** — `check_config` (per install type: `ha core check` on HA OS/Supervised;
   in-container on Container; `hass --script check_config` on Core), a timestamped backup, and a revert path gate every restart.
3. **Never edit `.storage/` while HA is running**, and never without a count-verified backup (tarball for whole-folder removals).
4. **Never append to `configuration.yaml`** — agent YAML lives in `packages/`, one file per subsystem.
5. **Never print or persist credentials outside `workspace/_memory/sensitive/`** — env vars at invocation time; scripts, logs, and the model stay credential-free.
6. **Unredacted host pulls stay in machine-local scratch** (`~/.superagent/tmp/`, per `rules/machine-local-home.md`) — only scrubbed distillations enter the workspace.
7. **Log** work that changes HA or workspace files to `interaction-log.yaml` as usual; the routine reads themselves are not logged.
