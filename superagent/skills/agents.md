# Superagent agents skill

Front-end to the agent roster defined in `contracts/agents.md`. A **role** is a file (`superagent/agents/<name>.agent.md`, or `workspace/_custom/agents/<name>.agent.md` for a custom role); an **instance** is a row in `_memory/agents.yaml`; an **id** is `<prefix>:<instance name>`, built by the tool from `config.preferences.autocode.id_prefix`. Never write an id by hand and never assume a prefix.

With no separate agents running (the default), this chat session takes whichever role the work needs. This skill is how it does that on request.

## 1. Preflight

1. Read `_memory/config.yaml` and resolve `preferences.workspace_path`. When it differs from the default, add `--workspace <path>` to every command below.
2. A line on stderr that starts with `agents:` names a problem in a role file or a registry row. Answer the question first, then relay the line: fixing a role file is the work of that role's dev twin (§ 2e).

## 2. Branch on intent

### 2a. Roster — "list agents", "who is on the roster"

```
uv run python -m superagent.tools.agents list
```

One row per agent: id, role, kind (`lead`, `durable`, `project`), status, host, and the id of its dev twin. A project role with no instance shows as `<prefix>:project:<slug>` with "no agent yet". Add `--json` for the model, cost cap and description of each. Relay the table as it is; one line of explanation per role comes from the `description` field.

### 2b. Id — "what is the id of the updater"

```
uv run python -m superagent.tools.agents id <name>          # updater, project:<slug>
uv run python -m superagent.tools.agents id <name> --dev    # the dev twin
```

Exit 2 names what is wrong (an unknown role, a project agent without a slug, a prefix that is not valid). Use the printed id whenever a session registers with a runtime under an agent's name.

### 2c. Duties — "which duties are overdue", "which agent runs the weekly review"

```
uv run python -m superagent.tools.agents duties [--agent <role>] [--due | --overdue]
```

One row per duty: agent, duty, skill, tier (`contracts/autonomy.md`), schedule, last run, state (`ok`, `due`, `overdue`, `unfinished`, `on-request`). A duty is `due` when its scheduled time has come and it has not run since, or its check found work (`contracts/update-loop.md` § 6); it is `overdue` once it is late. `--due` keeps what a scheduler would run now. `--overdue` keeps what is late, and prints nothing when all is current; these are the findings the on-open check prints. For each late duty, name the skill that clears it and offer to run it.

The check of one duty, as a scheduled wake would run it: `uv run python -m superagent.tools.agents check <agent> <duty>` (exit 0 due, overdue or unfinished, with the reason printed; exit 1 not due).

### 2d. Take a role — "act as the bookkeeper", "work on <project> as its agent"

1. Find the role with § 2a. Read its role file: `superagent/agents/<name>.agent.md`, or `workspace/_custom/agents/<name>.agent.md` for a custom role. When a framework role has a same-named file in `workspace/_custom/agents/`, read that too: it is an overlay of extra boundaries.
2. For the project role, also read the project's `info.md` and `status.md`, and the last entries of its `history.md`.
3. Say in one line which role the session took. Work inside that role's `skills` and boundaries. Work outside them belongs to another role: say so, and switch roles the same way.
4. The role's boundaries hold in full. One difference from a run with nobody present: the owner is here, so the session may ask.
5. Leave the role when the work is done or the owner changes the subject; the session is the lead again.

### 2e. Develop a role — "develop the updater agent"

The dev twin is the only writer of a role file, its duties and its checks (`contracts/agents.md` § 6).

1. Read `<name>.agent.dev.md` beside the role file, then `rules/framework-changes.md` for a framework role. A custom role is edited in `workspace/_custom/agents/` directly.
2. Check the gate: an approved row in `_memory/supertailor-suggestions.yaml` that names this agent, or the owner's direct request in this session. With neither, stop and say so.
3. Follow the workflow in `rules/framework-changes.md` § 7: plan, implement, test, commit only when the owner asked for commits.
4. After a change to a role file: `uv run python -m superagent.tools.build_agent_manifest`, and one new line in the dev twin's changelog.
5. When that agent runs as a session of its own, it has to re-read its role: tell the owner to send it `Pick up: <the change in one line>`, or send it when this session can.

### 2f. Add or change a registry row — "place the updater on <machine>", "set a cost cap for the bookkeeper"

A row gives an agent a setting (a host, a model, a cost cap, a status) and is how a project agent exists. One command creates or updates it; a field that is not given keeps its value:

```bash
uv run python -m superagent.tools.agents set <agent> [--host <machine>] [--status off|active|dormant|paused|retired] \
  [--model <provider/model>] [--variant <variant>] [--daily-usd <N>] [--project project:<slug>] [--notes "<text>"]
```

A new agent (a project agent, a custom role) is created with the `add-agent` skill, which gathers the charter first. Run § 2a afterwards and confirm the row shows with the id the owner expects.

### 2g. Grant a wake — "let the updater run every 30 minutes", "check the permit daily until March"

A periodic wake runs only with a grant the owner approved (`contracts/agents.md` § 8). The tool cannot see an approval, so the order matters:

1. Show the exact terms in one block: the agent, the wake's name, the trigger with its end (`every 30m`, `every 1d until 2027-03-01`), the duty whose check runs first, the purpose, the expected cost per run.
2. Get the owner's yes to those terms. A changed term is a new question. With nobody present, queue it (`uv run python -m superagent.tools.asks add --agent superagent --tier approve --key grant:<agent>:<wake> --question "..."`) and stop.
3. Record it, with the owner's words:

   ```bash
   uv run python -m superagent.tools.agents grant <agent> --wake <name> --trigger "<trigger>" \
     --purpose "<why>" --approval "<the owner's words>" [--duty <duty>] [--cost <usd>] [--ends <date>]
   ```

   It prints the wake's check, `uv run python -m superagent.tools.agents check <agent> [<duty>] --wake <name>`: exit 0 due, exit 1 not due or not granted. An agent under Autocode sets its wake with the line its start prompt gives, `sh superagent/tools/wake_check.sh <agent> [<duty>] --wake <name>`, which adds the daily cost cap in front of that check.
4. A grant takes effect when the agent sets the wake: at its next start, or after a `Pick up: wake <name> granted` message to a running agent.

Switch grants off and on with `agents grant <agent> [--wake <name>] --suspend` / `--resume` (a paused project), and remove one with `agents revoke <agent> --wake <name>`.

### 2h. Run agents as sessions of their own — "start the updater", "park the kitchen-renovation agent", "which agents are running"

**"Start superagent" is the `start` skill**: it asks the owner in question cards (the switch, the settings, which agents), records what was approved, makes the chat session the lead and starts the rest. This section is for one agent at a time, once the mode is on (`config.preferences.autocode.enabled`, `rules/autocode.md`). All of it goes through one tool, `uv run python -m superagent.tools.autocode`:

| Command | What it does |
|---|---|
| `start <agent> [--dev]` | Starts a session in this checkout with the model of the agent's tier and gives it the start prompt: register under the built id, read the rule and the role file, set the granted wakes and no other. Then marks the row (`active` with granted wakes, `dormant` without) and its host. `--print` shows the command and the prompt and starts nothing. |
| `park <agent>` | Asks the agent to write its state, compact and go idle; the row becomes `dormant`. |
| `stop <agent>` | Asks the agent to unregister; the row becomes `off`. |
| `retire <agent>` | Asks the agent to write its closing note and unregister; the row becomes `retired` and its grants are suspended. |
| `wakes [<agent>]` | Compares the wakes that are set with the grants: a wake with no grant, a grant with no wake, a trigger that differs. Exit 1 when something differs. |
| `status` | The roster against what is registered. |
| `setup` | The state and the proposed settings; `setup enable` / `disable` and `setup apply` are the `start` skill's writes. |
| `mark <agent>` | After this session registered as the agent: marks its row and host (`--off` after it unregistered). |
| `settings` | Prints optional Autocode settings lines (a hard cap, question routing, no expiry for idle agents). Nothing needs them, and it sets nothing. |

Rules for this section:

- **Starting an agent costs money and is the owner's call.** Start one only on the owner's yes in this session, after its wakes are granted (§ 2g).
- **`wakes` and `status` need the owner's shell** (a terminal on the Autocode server's machine). In an agent's own shell they say so; give the owner the command line.
- **Never ask the owner to edit a file or run a command.** Superagent's own settings are written by the tool on the owner's answer (`start` skill). Autocode's settings are the owner's and optional: show the lines `settings` prints only when the owner asks for them, and never run them.
- A dev twin (`start <role> --dev`) gets no wake and no row: it waits for the owner's request.
- After a change to a role file, a running agent needs `Pick up: <the change in one line>` (§ 2e).

### 2i. Interests — "what is the bookkeeper told about", "drop the kitchen agent's interest in <thing>"

An interest is one kind of update an agent asked the Updater to tell it about (`contracts/agents.md` § 8a). Each agent sets its own; this branch is for looking and for the owner's word.

```
uv run python -m superagent.tools.agents interest <agent>                     # its interests, one line each
uv run python -m superagent.tools.agents interest <agent> --remove <pattern>  # on the owner's word
uv run python -m superagent.tools.agents interest <agent> --add <pattern> --why "<what it does with it>" [--when changed|harvest|filed|captured] [--fire <wake>]
uv run python -m superagent.tools.agents interest <agent> --defaults          # the ones its role file names
uv run python -m superagent.tools.agents interested --when <kind> --handle <handle> [--handle ...]   # who would be told
```

A pattern is a handle or a handle glob (`project:<slug>`, `domain:finances`, `contact:<slug>`, `bill:*`). `--fire` takes a `fire-only` wake that is granted to the agent (2g). Twelve interests per agent at most; the Updater and a dev twin keep none. The daily briefing's agent lines (`agents heartbeat`) carry every agent's interests.

## 3. What this skill does not do

- It never starts an agent, grants a wake or changes a setting without the owner's word in this session.
- It does not create a role file. A new custom role is the `add-agent` skill's; a new framework role follows the Framework Artifact Creation Contract (`contracts/framework-artifacts.md`).
- It does not change a role's authority, and it never loosens a boundary (`contracts/autonomy.md` § 6).
