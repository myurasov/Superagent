# Superagent agents skill

Front-end to the agent roster defined in `contracts/agents.md`. A **role** is a file (`superagent/agents/<name>.agent.md`, or `workspace/_custom/agents/<name>.agent.md` for a custom role); an **instance** is a row in `_memory/agents.yaml`; an **id** is `<prefix>:<instance name>`, built by the tool from `config.preferences.autocode.id_prefix`. Never write an id by hand and never assume a prefix.

With no separate agents running (the default), this chat session takes whichever role the work needs. This skill is how it does that on request.

## 1. Preflight

1. Read `_memory/config.yaml` and resolve `preferences.workspace_path`. When it differs from the default, add `--workspace <path>` to every command below.
2. A line on stderr that starts with `agents:` names a problem in a role file or a registry row. Answer the question first, then relay the line: fixing a role file is the work of that role's dev twin (§ 2e).

## 2. Branch on intent

### 2a. Roster — "list agents", "who is on the roster"

```
uv run python -m superagent.tools.agents list
```

One row per agent: id, role, kind (`lead`, `durable`, `project`), status, host, and the id of its dev twin. A project role with no instance shows as `<prefix>:project:<slug>` with "no agent yet". Add `--json` for the model, cost cap and description of each. Relay the table as it is; one line of explanation per role comes from the `description` field.

### 2b. Id — "what is the id of the updater"

```
uv run python -m superagent.tools.agents id <name>          # updater, project:<slug>
uv run python -m superagent.tools.agents id <name> --dev    # the dev twin
```

Exit 2 names what is wrong (an unknown role, a project agent without a slug, a prefix that is not valid). Use the printed id whenever a session registers with a runtime under an agent's name.

### 2c. Duties — "which duties are overdue", "which agent runs the weekly review"

```
uv run python -m superagent.tools.agents duties [--agent <role>] [--overdue]
```

One row per duty: agent, duty, skill, tier (`contracts/autonomy.md`), schedule, last run, state (`ok`, `overdue`, `unfinished`, `on-request`). `--overdue` keeps what is late, and prints nothing when all is current; these are the findings the on-open check prints. For each late duty, name the skill that clears it and offer to run it.

The check of one duty, as a scheduled wake would run it: `uv run python -m superagent.tools.agents check <agent> <duty>` (exit 0 due with the reason printed, exit 1 not due).

### 2d. Take a role — "act as the bookkeeper", "work on <project> as its agent"

1. Find the role with § 2a. Read its role file: `superagent/agents/<name>.agent.md`, or `workspace/_custom/agents/<name>.agent.md` for a custom role. When a framework role has a same-named file in `workspace/_custom/agents/`, read that too: it is an overlay of extra boundaries.
2. For the project role, also read the project's `info.md` and `status.md`, and the last entries of its `history.md`.
3. Say in one line which role the session took. Work inside that role's `skills` and boundaries. Work outside them belongs to another role: say so, and switch roles the same way.
4. The role's boundaries hold in full. One difference from a run with nobody present: the owner is here, so the session may ask.
5. Leave the role when the work is done or the owner changes the subject; the session is the lead again.

### 2e. Develop a role — "develop the updater agent"

The dev twin is the only writer of a role file, its duties and its checks (`contracts/agents.md` § 6).

1. Read `<name>.agent.dev.md` beside the role file, then `rules/framework-changes.md` for a framework role. A custom role is edited in `workspace/_custom/agents/` directly.
2. Check the gate: an approved row in `_memory/supertailor-suggestions.yaml` that names this agent, or the owner's direct request in this session. With neither, stop and say so.
3. Follow the workflow in `rules/framework-changes.md` § 7: plan, implement, test, commit only when the owner asked for commits.
4. After a change to a role file: `uv run python -m superagent.tools.build_agent_manifest`, and one new line in the dev twin's changelog.
5. When that agent runs as a session of its own, it has to re-read its role: tell the owner to send it `Pick up: <the change in one line>`, or send it when this session can.

### 2f. Add or change a registry row — "place the updater on <machine>", "add an agent for <project>"

A row is needed to give an agent a setting (a host, a model, a cost cap) and to create a project agent.

1. For a project agent, the Project must exist (`projects` skill); its slug is the agent's slug.
2. Re-read `_memory/agents.yaml` right before the edit and change it in place (`rules/concurrent-sessions.md`). Copy the fields of the template row (`superagent/templates/memory/agents.yaml`): `name` (`<role>` or `project:<slug>`), `role`, `handle` (`agent:<name>`), `project` (`project:<slug>` for a project agent), `status: "off"`, and `provenance` (`source: user`, `at: <now>`). Leave `host`, `model`, `variant` and `daily_usd` null unless the owner named a value.
3. Never write a `wakes` entry on your own. A periodic wake is a grant the owner approves with its exact terms: trigger, purpose, cost per run, end date (`contracts/agents.md` § 8).
4. Run § 2a and confirm the new row shows with the id the owner expects.

## 3. What this skill does not do

- It does not start, stop or pause an agent's session, and it sets no wake. A session registers with a runtime only when the owner asks for that.
- It does not create a role file. A new role follows the Framework Artifact Creation Contract (`contracts/framework-artifacts.md`), starts from `templates/agents/agent.md` and `agent.dev.md`, and defaults to `workspace/_custom/agents/`.
- It does not change a role's authority, and it never loosens a boundary (`contracts/autonomy.md` § 6).

## 4. Logging

A roster, id or duties query (§ 2a to § 2c) is read-only and needs no log row. Log one row through `signals log` when the session took a role (§ 2d), developed one (§ 2e) or changed the registry (§ 2f):

```yaml
- id: "<minted by signals log>"
  ts: "<ISO 8601 datetime with offset>"
  skill: "agents"
  action: "<take-role | develop | registry>"
  summary: "<role or agent handle> — <what was done, in one line>"
  related_project: null     # the project, for a project agent
  action_items: []
```
