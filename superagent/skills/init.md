# Superagent initialization skill

Follow these steps in order. Use the repo root as the working directory unless `workspace/_memory/config.yaml` already defines a different `preferences.workspace_path`.

## 1. Welcome message

Open with a brief 4-line welcome:

- **Superagent** is a personal-life AI assistant — it shadows you across bills, health, home, family, and the rest of your life so the admin overhead stops crowding out the work that matters.
- This setup takes about **5 minutes** for the quick-start path: a 4-question questionnaire, scaffold a folder structure, and try a couple of capture commands. No data sources required.
- Optional **data-source path** (after the quick-start): probe which shipped watcher packs (SimpleFIN, Gmail, …) are already set up on your machine, and enable the ones you want. You can also run `watch probe` later.
- Everything stays **local** in `workspace/` (gitignored). No telemetry, no cloud sync, no remote write.

Then immediately proceed to step 2.

## 2. Quick-start questionnaire (mandatory)

Use the `AskQuestion` tool. **One batch**, a handful of questions, takes a minute.

If the harness renders an `allow_multiple` question (Q2, Q3) as single-select, accept the first pick, then ask ONE plain-text follow-up ("Anything else? Comma-separated.") and merge the answers into the same field — do not re-issue the structured question.

**Question 1 — "What should I call you?"** (text-input style — present a couple of common options and a "type a name" escape):

Options:
- "Use my Git name"
- "Use my macOS account name"
- "Let me type it"

(If the user picks "Let me type it", prompt for the value in the next message.)

**Question 1b — "What's your personal email?"** (text-input style — used by skills like `draft-email`, `handoff`, and outbound templates so you don't have to type it each time):

Options:
- "Use my Git email" (from `git config user.email`)
- "Let me type it"

(If the user picks "Let me type it", prompt for the value in the next message. The harness-injected `# userEmail` block is the user's IDE / login email and is NOT a substitute — it may be a work address even when this is a personal workspace.)

**Question 2 — "Who is in your household?"** (allow_multiple: true)

Options:
- Just me
- Spouse / partner
- Kids
- Parents (live with you)
- Roommates
- Dog(s)
- Cat(s)
- Other pet(s)
- Other (I'll describe)

**Question 3 — "What's the most painful personal-admin friction RIGHT NOW?"** (allow_multiple: true)

Options:
- Bills — I miss due dates, forget recurring charges, or fight late fees
- Subscriptions — I have no idea what I'm paying for
- Health — I can never remember when I last saw the dentist / had labs / refilled X
- Important dates — birthdays, anniversaries, recurring deadlines slip
- Appointments — booking, prep, follow-up takes too much energy
- Documents — I can never find the passport / title / insurance card when I need it
- Home maintenance — filters, HVAC, gutters, anything seasonal falls through
- Vehicles — service intervals, registration, insurance renewals slip
- Pets — vet schedule, meds, food rotation
- Family logistics — kids' schedules, school stuff, parent care
- Email triage — too much, hard to prioritize
- Finances — I don't know where my money goes
- Hobbies / fitness — I lose track of progress
- Just feeling overwhelmed — I want one place that knows everything

Capture answers — they drive (a) seeded `_memory/insights.yaml` rows, (b) which capture skill the walkthrough demos in step 7, (c) which optional data sources to recommend with priority in step 5.

**Question 4 — "How far back should spreadsheet exports reach?"** (single-select)

Per the workbook subsystem (see `skills/workbooks.md`), Superagent renders
human-friendly `.xlsx` projections of your structured data — Bills,
Transactions, Vet Visits, Service History, etc. Time-series sheets respect
this window; reference sheets (Accounts, Properties, Certifications) ignore
it.

Options:
- 5 years
- **10 years** (default — covers most personal-tax + net-worth cases)
- 20 years
- All available history (no truncation)

Captured into `_memory/config.yaml.preferences.workbooks.history_window_years`.

## 3. Scaffold the workspace

Run `uv run python superagent/tools/workspace_init.py`. The script:

1. Creates `workspace/` if missing.
2. Creates `workspace/_memory/` and copies every YAML template from `superagent/templates/memory/` into it (only if the destination file doesn't exist; never overwrite user data). The shipped `domains-index.yaml` template **registers** the 13 default domains so capture skills can route to them; `watchlist-state.yaml` is seeded empty (machine-owned run state for the watchlist, per `contracts/watchlist.md`).
3. Creates `workspace/Domains/` (the directory only — per-domain folders are LAZY per `contracts/domains-and-assets.md` § 6.4a; they materialize the first time data lands for a given domain). Drops the explanatory `Domains/README.md` template explaining the convention.
4. Creates `workspace/Projects/` (empty; populated as the user adds projects via `add-project`).
5. Creates `workspace/Sources/` with `documents/`, `references/`, `_cache/`, and `Watchlist/` subdirectories (per the immutability + caching contract in `contracts/sources.md`; `Watchlist/` is the watcher registry — a reserved name with user-editable contents, one `<id>.ref.md` per watcher).
6. Creates `workspace/Inbox/`, `workspace/Outbox/`, `workspace/Archive/`, and drops the explanatory README from `superagent/templates/folder-readmes/` into each.
7. Creates `workspace/_custom/` with empty `rules/`, `skills/`, `agents/`, `templates/`, `tools/`, `watchers/` subdirectories (per the custom-overlay contract; `watchers/<id>/` holds user-authored watcher packs).
8. Creates the workspace-level `workspace/todo.md` from `superagent/templates/todo.md` (with no rows yet).
9. Stamps `workspace/.version` with the framework's current version (per `contracts/versioning.md` § 2 + § 6 — every workspace records the framework version it was scaffolded from so future framework upgrades can compute the correct migration chain via the `migrate` skill).
10. Records workspace-init timestamp in `_memory/interaction-log.yaml`.

Read back the script's stdout to the user as confirmation; surface any errors.

## 4. Populate `config.yaml` from the questionnaire

Open `workspace/_memory/config.yaml` and fill in:

- `last_updated` → now (ISO 8601 with TZ).
- `profile.preferred_name` from Q1 (with fallback to git or macOS user name if "Use my X name" was picked).
- `profile.email` from Q1b (resolve "Use my Git email" via `git config user.email`).
- `profile.timezone` from system as an **IANA zone name** (e.g. `America/Los_Angeles`): `readlink /etc/localtime | sed 's|.*/zoneinfo/||'` on macOS / Linux, or `timedatectl show -p Timezone --value` on systemd hosts. Do NOT use `date +%Z` — it yields an abbreviation (`PDT`), which `config.yaml.preferences.timezone` must not hold.
- `profile.household_composition` from Q2 (concatenated short text, e.g. "spouse + 2 kids + 1 dog").
- `preferences.pain_points` from Q3 (the option ids).
- `preferences.workbooks.history_window_years` from Q4 (5 / 10 / 20 / null for "all").

If Q3 included specific pain points, also seed `_memory/insights.yaml` with one row per pain point mapping it to the recommended skill (see § 8 mapping reference).

## 4b. IDE-specific support files (verify presence)

Both **Cursor** and **Claude Code** are first-class host IDEs, and any other `AGENTS.md`-reading CLI works with zero framework changes (see `AGENTS.md` § "Harness setup (Cursor, Claude Code, and other CLIs)"). The framework distribution includes four shim files at the repo root, all tracked in git:

| Path | Purpose |
|---|---|
| `CLAUDE.md` | Claude Code's entry point — pure `@AGENTS.md` re-export |
| `.claude/settings.json` | Claude Code project settings — wires `UserPromptSubmit` to `superagent/tools/log_user_query.py --source claude-code` AND `PostToolUse` matchers for the three Gmail MCP tools to `superagent/tools/email/archive_hook.py` (per `contracts/email-capture.md` capture-on-touch) |
| `.claudeignore` | Tells Claude Code to skip `.cursor/` and `workspace/` for ambient context |
| `.cursor/hooks.json` | Cursor hook config (schema `"version": 1`, Cursor-native event names) — wires `beforeSubmitPrompt` to `superagent/tools/log_user_query.py` (default `source=cursor`) AND a single matcher-less `afterMCPExecution` entry to `superagent/tools/email/archive_hook.py --kind=auto`. NOT a mirror of `.claude/settings.json`: Cursor silently loads nothing if Claude Code's `UserPromptSubmit` / `PostToolUse` names are used here (per `contracts/email-capture.md` § 8.1) |

A fresh `git clone` has all four. If any is missing (the user accidentally deleted one, or pulled a pre-0.5.0 clone), surface the discrepancy and recommend `git checkout -- <path>` to restore from the framework's reference content. The init skill does NOT auto-create them — they are framework distribution, not workspace data.

After this step, confirm IDE detection works from the user's current shell:

```bash
uv run python -m superagent.tools.ide current   # should print claude-code, cursor, or unknown
```

A result of `unknown` is fine for the duration of init (init runs the same way under either IDE); it just means neither IDE's environment markers are set in the shell where init was invoked.

## 4c. MCP config bootstrap (per-IDE runtime files)

Each IDE reads its own project-level MCP runtime file (Cursor: `.cursor/mcp.json`; Claude Code: `.mcp.json`). Both are gitignored — they may carry auth tokens. The committed templates (`.cursor/mcp.json.cursor` and `.mcp.json.claude`) ship with the framework and are content-identical (Superagent has no per-IDE OAuth client_id constraint).

For each runtime file:

1. **`.mcp.json`** (Claude Code runtime). If missing: copy `.mcp.json.claude` → `.mcp.json` as a **regular-file copy**. If it already exists as a regular file, leave it alone — the user owns it after init.
2. **`.cursor/mcp.json`** (Cursor runtime). If missing or a **legacy symlink** (pre-`0.5.0` workspaces sometimes symlinked it to `.mcp.json`): copy `.cursor/mcp.json.cursor` → `.cursor/mcp.json` as a regular-file copy. If a symlink is detected, show the user the current target and ask via `AskQuestion`: `replace with copy from .cursor/mcp.json.cursor / skip`. Default: replace. If it already exists as a regular file, leave it alone.

**Never use symlinks.** This repo lives in iCloud Drive on most user machines; iCloud occasionally rewrites symlinks as placeholders across machines, which silently breaks the dual-IDE setup. Regular-file copies are robust.

**Drift detection.** If both `.mcp.json` and `.cursor/mcp.json` already exist but their contents differ (user edited one and forgot to mirror), print a short one-screen unified diff and ask via `AskQuestion`: `mcp.json → mirror to .cursor / .cursor/mcp.json → mirror to root / show full diff / leave as-is`. On either copy choice, run the copy and re-verify identity. There is intentionally no `tools/mcp_sync.py` helper — the per-init prompt is enough at single-user volume.

After this step, print one short pointer: *"MCP runtime files in place. Add servers by editing whichever file your IDE reads; re-run `init` to mirror. Per-source auth procedures (SimpleFIN, Gmail) live in `superagent/docs/data-sources.md`."*

## 5. Probe for available data sources (optional, opt-in)

Ask the user (single question):

> "Want me to look for data sources I could watch? I'll check which of the shipped watcher packs are already set up on this machine and ask before enabling each one. (No data is read in this step — only presence checks.) **yes / no / later**"

If the user picks **no** or **later**, skip to step 6.

If the user picks **yes** (per `contracts/watchlist.md`; the `watch` skill is the standalone form of this step):

1. Probe every shipped pack's declarative `probe:` block in one call (no arguments = every pack, framework and `_custom/watchers/`; `--all` would instead probe the already-registered watchers, of which a fresh workspace has none):

   ```bash
   uv run python -m superagent.tools.watchlist probe
   ```

   The output is the presence table — `available` / `needs setup` per pack (`simplefin`: the claimed credentials file exists; `gmail`: the Gmail MCP token at `~/.gmail-mcp/credentials.json` exists; `url` / `subagent`: always available — they need a target, not a setup).
2. **Prioritize** by the user's pain points from Q3 ("Finances" / "Subscriptions" → `simplefin`; "Email triage" / "Bills" / "Important dates" → `gmail`) and by value-per-minute-of-setup.
3. **For each available pack**, ask:

   > "I found **<pack>** set up. Enabling it registers a watcher in `Sources/Watchlist/` that <one-line summary — e.g. checks live for new mail matching a query / pulls bank and brokerage transactions weekly>. **Enable now / enable later / skip**?"

   On "enable now":

   ```bash
   uv run python -m superagent.tools.watchlist enable <pack> --id <id> [--param key=value]
   ```

   `gmail` is parameterized — ask for the query and pick a stable id (`--id gmail-bills --param query="label:Bills newer_than:30d"`). The command writes `Sources/Watchlist/<id>.ref.md` from the template; the pack's `schedule` / `capture_mode` defaults are preserved (`simplefin` stays weekly + manual).
4. **For each `needs setup` pack the user expressed interest in**, point at `superagent/docs/data-sources.md#<pack>` (`superagent/watchers/simplefin/claim.py` for SimpleFIN; the Gmail MCP auth flow for Gmail) and say: *"I can pick this up any time — say `watch probe`."*
5. Anything without a pack (a portal, a permit page, a status URL) is a bare `url` / `subagent` watcher — offer the `watch` skill later rather than here.

### 5b. First check (per watcher the user enabled)

1. Run one check so each new watcher gets its baseline fingerprint:

   ```bash
   uv run python -m superagent.tools.watchlist check --cycle daily-update --report
   ```

2. For `simplefin` (`capture_mode: manual`) offer the first harvest explicitly — never silently: *"Pull the first 90 days of transactions now? (yes / later)"* → `uv run python -m superagent.tools.watchlist harvest --id simplefin`. Surface the one-line summary from the `ingestion-log.yaml` row it appends.
3. On failure, log the error and keep going — no watcher's failure aborts the rest.
