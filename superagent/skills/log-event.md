# Superagent log-event skill

This is the catch-all "I just did / experienced / heard X — record it" capture skill. The agent figures out from context which sub-flow to run.

> **Pre-flight (lazy-materialization contract — `contracts/domains-and-assets.md` § 6.4a)**:
> This skill writes to `Domains/<domain>/history.md` (and sometimes
> `rolodex.md`) for whichever domain the event resolves to. After step 1
> classifies the event and the target domain is known, run:
>
>     uv run python -m superagent.tools.domains ensure <domain-id>
>
> BEFORE the first append. Sub-flows that delegate to a dedicated skill
> (`health-log`, `pet-care`, `bills`) inherit that skill's own ensure call —
> no duplicate needed.

## 1. Classify the event

Heuristics:

| If the event mentions … | Sub-flow |
|---|---|
| a medical / dental / vet provider in `contacts.yaml`, OR a kind word ("appointment", "visit", "checkup", "exam", "shot") | **medical** (delegate to `health-log`) |
| a vehicle in `assets-index.yaml`, OR words "service", "oil change", "tire rotation", "brakes", "mileage", "fuel" | **vehicle** (handled here, § 2 — `Domains/Vehicles/history.md` + the vehicle's asset row) |
| a vehicle plus "accident", "crash", "collision", "fender-bender", "hit" | **vehicle accident** (handled here, § 2 — history + P0 claim task + document rows) |
| a vehicle plus "registration", "inspection", "insurance renewal", "renewed", "sticker" | **vehicle renewal** (handled here, § 2 — `documents-index.yaml` expiry + `bills.yaml` payment row) |
| home / appliance, OR "repair", "service", "filter", "HVAC", "plumber", "electrician", "contractor" | **home** (handled here, § 2 — `Domains/Home/history.md` + the asset row when one applies) |
| "what's due", "what maintenance is due", "schedule" + a maintenance kind (filter, gutters, oil change, pest control) — nothing happened yet | **maintenance schedule** (§ 3 — list due / schedule; no history append) |
| a pet in `contacts.yaml` (role: pet) | **pet care** (delegate to `pet-care`) |
| a bill / payment / charge | **bill** (delegate to `bills mark-paid`) |
| "talked to <person>" / "had coffee with <person>" / "called <person>" | **interaction** |
| "log this decision" / "we decided" / "I decided" | **decision** (append a row to `_memory/decisions.yaml` per `contracts/decisions.md` — required: `id`, `ts`, `decision`, `context`, `confidence`, `reversibility`; encouraged: `rationale`, `review_at`; also append to the relevant domain/project `history.md`) |
| anything else | **generic** (append to relevant domain history) |

If multiple plausible matches, ask the user which sub-flow.

## 2. Sub-flow execution

For **medical**, **pet care** and **bill**, delegate to the dedicated skill (`health-log`, `pet-care`, `bills`).

For **vehicle** and **home** (asset-bound events):

1. Resolve the asset in `_memory/assets-index.yaml` — a vehicle by name, plate, or make / model; a home system or appliance by name (`grep -n` the file for the words the user used; never load it whole). Offer `add` (asset) when the thing is clearly an asset the user owns but has no row. A one-off home repair with no asset behind it (a plumber fixing a leak) proceeds with no asset row.
2. Ask only for what the prompt left out: date (default today), what was done, who did it (a contact — offer `add-contact` when new), cost, odometer reading (vehicles), and whether a recurring interval applies (oil every 5,000 mi; filter every 90 days).
3. Run the pre-flight `domains ensure` for `vehicles` or `home`, then prepend an H4 entry to `Domains/Vehicles/history.md` or `Domains/Home/history.md` (`#### YYYY-MM-DD — <one-line title>`, newest at the top, body free-form: provider, cost, odometer, parts, notes).
4. Update the asset row when one exists: `mileage` (vehicles), and the matching `maintenance[]` item's `last_done` / `next_due` (`next_due` = `last_done` + `interval_days`; compute it from the interval when the user gave one). Call `record_change` per `contracts/audit-trail.md` BEFORE saving so the transition lands in `assets-index.yaml.history.jsonl`; then `uv run python -m superagent.tools.render_domain --domain <vehicles|home>` to refresh the derived blocks. A completed maintenance item also closes any matching open P-task in `todo.yaml` (grep by asset slug + kind) and syncs `Domains/<Vehicles|Home>/status.md`: one bullet under § Recent Progress, and § Next Steps refreshed with the next 1-3 due items from the asset's `maintenance[]`.
5. If money changed hands and the user has (or can produce) a receipt or invoice, follow `contracts/payment-confirmations.md` — file it under `Sources/` via `add-source` and cross-link from the history entry.
6. Rolodex: add or update the provider's row in `Domains/<Vehicles|Home>/rolodex.md` (`Last contacted` ← `ts` of the event) per `contracts/domains-and-assets.md` (rolodex sync).
7. Create a P2 task in `todo.yaml` for each follow-up the user names (a part on order, a re-check in two weeks); when a `next_due` was computed, no task — `daily-update` § "Maintenance windows" surfaces it from the asset row.

For **vehicle accident** (steps 1 and 3 of the vehicle flow apply; then):

1. Ask only for what the prompt left out: date, location, severity (minor / fender-bender / serious), the other parties (name, insurer, plate), whether a claim was filed (and the claim number), and the insurance contact.
2. The H4 entry in `Domains/Vehicles/history.md` carries the full details: parties, damage, claim number, insurer contact, next step.
3. Claim filed → create a **P0** task in `todo.yaml`: "File / follow up on insurance claim for <date> accident" (`related_asset: <vehicle slug>`, due in 3 days unless the user names a date). No claim → ask once whether to file one; a "yes" creates the same P0 task.
4. Photos, the police report, the claim letter: file each via `add-source` (HEIC converts to JPEG per `rules/image-format-policy.md`), then register a `documents-index.yaml` row through the `add` skill, kind `document` (`kind: other`, title "Police report — <date> accident" / "Accident photos — <date>", `domain: vehicles`, `path` = the placed file, `sensitive: false`). One row per artifact set; none when the user has nothing to file.
5. The other party (and a new insurer or adjuster) → `add-contact` (role `other` / `vendor`, notes naming the accident date); the contact id goes into the history entry.
6. Update the vehicle row when the accident changes it (`insurance`, `notes`, `status: repairing`); `record_change` before saving, `render_domain --domain vehicles` after.

For **vehicle renewal** — registration / inspection / insurance (steps 1 and 3 of the vehicle flow apply; then):

1. Ask: which renewal (registration / inspection / insurance), date renewed, the new `expires_at`, cost, and where the sticker / certificate / insurance card lives.
2. `documents-index.yaml` — grep for the vehicle's registration card / inspection certificate / insurance policy row (by `domain: vehicles` + title). Existing row → refresh `expires_at` (plus `issued_date` and `physical_location` when they changed) with `record_change` per `contracts/audit-trail.md`; no row → create it through the `add` skill, kind `document` (`kind: other` for registration / inspection, `insurance_policy` for the policy; `domain: vehicles`, `expires_at`). The row's `expires_at` is what `daily-update` / `monthly-review` surface — no separate important date unless the user asks.
3. `bills.yaml` — the renewal payment goes through the `bills` skill: a bill row for this renewal exists (registration renewal / insurance premium, often seeded by `add` § 7 when the vehicle was registered) → `bills` mark-paid mode appends the `history[]` row, advances `next_due`, and captures the confirmation per `contracts/payment-confirmations.md`; no row → `bills` Add mode first (`cadence` annual or per policy term, `domain: vehicles`, `asset: <slug>`), then mark-paid.
4. The vehicle's matching `maintenance[]` row (`registration renewal` / `inspection` / `insurance renewal`) gets `last_done` = date renewed and `next_due` = `expires_at`; the H4 history entry names the new expiry and the document row.

For **interaction**:

1. Resolve the contact (offer `add-contact` if missing).
2. Ask: when, summary, action items.
3. Append to `_memory/interaction-log.yaml` in the canonical row shape
   (`templates/memory/interaction-log.yaml` is normative — never the retired
   `timestamp` / `type` / `subject` / `participants` keys). Name the contact
   in `summary`; there is no `participants` field.
   ```yaml
   - id: "<ilog-YYYY-MM-DD-NNN via uv run python -m superagent.tools.next_id --kind ilog --file _memory/interaction-log.yaml>"
     ts: "<when — ISO 8601 datetime with offset>"
     skill: "log-event"
     action: "<meeting|call|note> with <contact name>"
     summary: "<what was discussed / decided with <contact name>>"
     related_domain: <inferred from contact's primary related_domain, or null>
     related_project: null
     related_asset: null
     related_account: null
     action_items: <list>
     ingestion_log_ref: null
   ```
4. For each action item, create a P2 task in `todo.yaml`.
5. Update `Domains/<related_domain>/rolodex.md` row for the contact: `Last contacted` ← `ts`.
6. Optionally append to `Domains/<related_domain>/history.md` if the interaction was substantive.

For **generic**:

1. Ask: which domain.
2. Append H4 entry to `Domains/<Domain>/history.md` with the user's text.
3. Capture any obvious follow-ups as P2 tasks.

## 3. List due / schedule maintenance

The home and vehicle maintenance schedule lives on the asset rows (`assets-index.yaml.<asset>.maintenance[]`: `kind`, `interval_days`, `interval_miles`, `last_done`, `next_due`). Completion is § 2 step 4; this section covers the two intents where nothing has happened yet.

### List due — "what's due on the house", "what maintenance is due"

1. Filter `_memory/assets-index.yaml` in a tool (`yaml.safe_load` + filter, or `grep -n` for the asset names — never load it whole into context): assets with `status: active` and `domain` in `home` / `vehicles` (or only the domain the user named), then every `maintenance[]` row on them.
2. Bucket by `next_due` against today, capped at `config.preferences.surfacing.maintenance_lookahead_days` (default 30): **Overdue** (`next_due < today`), **Due in the next 7 days**, **Due in the next 30 days**. A vehicle row with `interval_miles` is also due when the vehicle's current `mileage` has passed the odometer recorded in the last matching service entry in `Domains/Vehicles/history.md`. A row with `next_due: null` is listed once under "never scheduled".
3. Format one line per item, grouped by bucket: `{asset} → {kind} (due {next_due}, last done {last_done})`. Nothing due → say so and name the next upcoming item.
4. Pure read: no `domains ensure`, no history append. Offer completion (§ 2) for anything the user says is already done, and § "Schedule" for anything missing.

### Schedule — "schedule a gutter cleaning", "schedule a home maintenance task"

1. Resolve the asset (offer `add`, kind `asset`, when it has no row). Ask only for what is missing: kind, `interval_days` (and `interval_miles` for vehicles), `last_done` if known — or the date the first occurrence should be due.
2. Append to `assets-index.yaml.<asset>.maintenance[]` (`record_change` per `contracts/audit-trail.md` before saving):

   ```yaml
   - kind: "<kind>"
     interval_days: <n>
     interval_miles: <n or null>      # vehicles only
     last_done: <date or null>
     next_due: <last_done + interval_days, or the first due date the user gave>
   ```

   Then `uv run python -m superagent.tools.render_domain --domain <home|vehicles>`. An asset whose `maintenance[]` was empty gets the default schedule for its kind offered from the `add` skill § 7 (asset) table.
3. `next_due` within 30 days → one P2 task in `todo.yaml` ("<kind> — <asset>", due `next_due`, `related_asset: <slug>`); otherwise none — `daily-update` § "Maintenance windows" surfaces it from the asset row.
4. Run the pre-flight `domains ensure <home|vehicles>`, then refresh `Domains/<Home|Vehicles>/status.md` § Next Steps with the next 1-3 due items across that domain's assets.

## 4. Confirm

```
Logged <event-type> in <domain> on <date>.
Action items captured: <count>.
```

For a vehicle / home event add the asset line: `<asset>: <field> updated; next due <date or "—">.`
For an accident add: `Claim: <filed / not filed>; P0 task <id or "none">; documents filed: <count>.`
For a renewal add: `<document> now expires <expires_at>; payment logged on <bill id or "no bill">.`
For a schedule add: `Scheduled <kind> on <asset> every <interval>; first due <next_due>.` List-due answers with the bucketed list and no confirmation line.

## 5. Logging

**interaction** already appended its row in step 2. Every other sub-flow this skill handled itself (vehicle, vehicle accident, vehicle renewal, home, generic, decision, list due, schedule) appends one canonical row (mint the id with `uv run python -m superagent.tools.next_id --kind ilog --file <workspace>/_memory/interaction-log.yaml`):

```yaml
- id: "<ilog-YYYY-MM-DD-NNN>"
  ts: "<now — ISO 8601 datetime with offset>"
  skill: "log-event"
  action: "<vehicle_event|vehicle_accident|vehicle_renewal|home_event|generic_event|decision_logged|list_maintenance_due|schedule_maintenance>"
  summary: "<one line: what was logged, where>"
  related_domain: <vehicles|home|<domain>>
  related_asset: <asset id or null>
  action_items: <task ids created, or []>
  ingestion_log_ref: null
```

Delegated sub-flows (`health-log`, `pet-care`, `bills`) log under their own skill name.
