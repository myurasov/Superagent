# Superagent add-source skill

> **Pre-flight (lazy-materialization contract — `contracts/domains-and-assets.md` § 6.4a)**:
> When invoked with `--to-domain <id>`, this skill writes to
> `Domains/<Domain>/sources.md`. Before that write, run:
>
>     uv run python -m superagent.tools.domains ensure <domain-id>
>
> Idempotent. Skips when the source is project-scoped only
> (`--to-project <slug>` without `--to-domain`).

The Sources contract is in `contracts/sources.md`. This skill is the document capture front-end. Remember: `Sources/` has a **user-defined layout**. The agent reserves only `Sources/README.md` and the `Sources/Watchlist/` name (the watcher registry — user-editable contents, per `contracts/watchlist.md`). Everything else is the user's territory; this skill SUGGESTS paths but the user can always override.

## 0. Resolve the destination domain / project

The most common invocation is **"add this to <domain>"** or **"add X to <project>"** — where `<domain>` / `<project>` is the user's natural-language reference to a row in `_memory/domains-index.yaml` / `_memory/projects-index.yaml`.

Resolution flow:

1. If the trigger phrase contains a domain name or slug, set `--to-domain <id>`.
2. If the trigger phrase contains a project name / slug, set `--to-project <id>`.
3. If both, set both — the source will appear in both `sources.md` files.
4. If neither (e.g. "add this PDF to Sources" with no domain hint), infer from:
   - `category` once chosen (e.g. category `medical` → `--to-domain health`).
   - The active domain in `_memory/context.yaml.current_focus` if recent.
   - Otherwise ask the user.

This step ALWAYS resolves before file placement so the skill knows what to cross-link in step 4.

## 1. Document or watcher?

This skill files **documents** — a local file the user keeps. If what the user describes is something that lives elsewhere and should be **watched for change** — "watch this page", "tell me when the permit status moves", "alert me on new mail matching X", a bank feed, a portal behind a login — it is a **watcher**, not a document: stop here and continue in the `watch` skill, which writes `Sources/Watchlist/<Title_Case>.ref.md` (`contracts/watchlist.md`). There is no third kind: a URL or portal the user merely wants to remember goes in the relevant domain's `info.md` / `rolodex.md`, not into `Sources/`.

Ask only if it is not obvious from the trigger:

> "Is this a document to keep here, or something to watch for changes?"

Anything under `Sources/` ending `.ref.md` IS a watcher (`contracts/sources.md` § 15.4) — never write one from this skill.

## 2. Collect metadata and place the document

The user provides a path (or has just dropped a file in `Inbox/`). Steps:

1. Resolve the file. If in `Inbox/`, propose moving it. A HEIC / HEIF photo is converted to JPEG first (`rules/image-format-policy.md`).
2. **Category** (optional, free-text tag): ask the user, or infer from filename + content. Common values: `vehicles`, `taxes`, `medical`, `warranties`, `legal`, `insurance`, `property`, `education`, `pets`. The user can pick anything; categories are tags only — they do not constrain the path.
3. **Title**: short, e.g. "Camry title 2018", "2024 federal return".
4. **Suggest a destination path** based on the category and any existing folder structure under `Sources/`. Examples:
   - `vehicles` → `Sources/vehicles/<vehicle-slug>/<filename>` (or just `Sources/vehicles/<filename>` if no `<vehicle-slug>`).
   - `taxes` → `Sources/taxes/<year>/<filename>`.
   - `medical` → `Sources/medical/<member-slug>/<filename>`.
   - `warranties` → `Sources/warranties/<asset-slug>/<filename>`.
   - `legal` → `Sources/legal/<filename>`.
   - `<custom>` → `Sources/<category>/<filename>`.
   Then **ask the user to confirm or override**: "I'll put this at `<suggested-path>` — accept, or pick another path?" Paths follow `rules/file-naming.md` — no spaces in new components.
5. **For member** (only if relevant): self / name / household.
6. **Cross-references** (optional):
   - `related_domain` (auto-suggest from category).
   - `related_project` (e.g. tax docs → `tax-<year>`).
   - `related_asset` (e.g. vehicle title → `<vehicle-slug>`).
   - `related_account` (statements, payment confirmations).
7. **Sensitive?**: default false; flip true for medical, legal, accounts.
8. **Notes**: free text.

**Move** the file to the chosen path if it comes from `Inbox/` — never copy and leave the original. Copy only if the source is outside `Inbox/`. After moving from `Inbox/`, record the decision in `workspace/_memory/inbox-log.yaml` via `uv run python -m superagent.tools.inbox_triage record --file <inbox filename> --action filed --destination <path> --note "<note>"` (never hand-append YAML rows; include the sources-index id in the note once assigned).

**Sidecar (optional).** When the document needs metadata the index row cannot hold on its own — structured fields (a payment confirmation's `payee` / `amount` / `payment_date` per `contracts/payment-confirmations.md` § 2), a story worth keeping next to the file, a `provenance` block — write `<filename>.meta.md` beside it (`contracts/sources.md` § 15.3; the name is the document's FULL filename plus `.meta.md`):

```yaml
---
title: "<title>"
description: "<one-liner>"
sensitive: <bool>
related_domain: "<id>"
related_project: "<id>"
related_asset: "<id>"
related_account: "<id>"
added_by: "user"
added_at: <now>
tags: <list>
---

<notes>
```

Skip the sidecar when everything fits in `_memory/sources-index.yaml` (its hand-curated fields survive refreshes). Never name a sidecar `.ref.md` — that suffix means watcher.

## 3. Refresh the index

After placement:

1. Run `uv run python -m superagent.tools.sources_index refresh`. The walker picks up the new file and writes a row to `_memory/sources-index.yaml` with:
   - `id` derived from the workspace-relative path
   - `kind: document`, `title`, `path`, `category`
   - `present: true`, `read_count: 0`, `added: <now>`
   - any cross-references parsed from the `.meta.md` sidecar's frontmatter
2. If you collected additional fields the agent should remember (notes, sensitive, related_*) and wrote no sidecar, edit the row's hand-curated fields in `_memory/sources-index.yaml` in place — `sources_index` has no field-setting subcommand (its subcommands are `refresh` / `list` / `get` / `by-path` / `touch` / `remove`); refresh preserves `notes`, `tags`, `sensitive`, and `related_*` on subsequent runs.

The index is **derived from the filesystem**. The user can drop a file by hand from a shell at any time; the next read of `_memory/sources-index.yaml` triggers a refresh that picks it up. `add-source` is the convenience path; it does not own placement.

## 4. Cross-link to sources.md (the most important step)

**This is the contract that distinguishes `add-source` from a raw file copy.** Every source MUST be reachable from the human-readable per-domain / per-project catalogue:

### 4a. Per-domain `sources.md` write

If `related_domain` is set:

1. Open `workspace/Domains/<Domain>/sources.md`.
2. Resolve the `## Documents` table (watchers have their own `## Watchers` table, written by the `watch` skill — never from here).
3. Append a new row using the row format defined in the template (`superagent/templates/domains/sources.md`):
   `| <title> | <workspace-relative path> | <category> | <added-date> | <notes — mention the .meta.md sidecar when one exists> |`.
4. If the row already exists (same path), update notes only — do not duplicate.
5. Update the `_Last updated:_` timestamp at top of the file.
6. Respect hand-edits: if the user has restructured the file (added custom sub-headings, regrouped rows, added a commentary paragraph), the skill performs a careful diff-and-merge, not a blind rewrite. Find the right table by header + columns, never by line number.

### 4b. Per-project `sources.md` write

If `related_project` is set: same routine as 4a, but against `workspace/Projects/<slug>/sources.md`. Plus the project may have its own `Projects/<slug>/Sources/` sub-tree — if `--scope project` was passed, the actual file ALSO goes under `Projects/<slug>/Sources/<your-path>` (project-scoped) instead of the workspace-level `Sources/<your-path>`.

A source can have BOTH `related_domain` AND `related_project` set — the row appears in both files.

### 4c. Asset cross-link

If `related_asset` is set: append the workspace-relative path to `_memory/assets-index.yaml.<asset>.receipts[]` (for receipts) or `.photos[]` (for photos that are vault-grade — i.e. retained for insurance) or as a free-form `notes` reference (for other docs).

### 4d. Account cross-link

If `related_account` is set: append the path to `_memory/accounts-index.yaml.<account>.notes` as a single-line reference. (Per-account documents like statements typically belong to the Finances domain's `sources.md` AND get this account-level back-pointer.)

## 5. Confirm

```
Added document "<title>" to <path>.
Sidecar: <path>.meta.md | none.
Cross-references: <list>.
Sensitive: <yes/no>.
Index id: <id>.
```

If the user also wants to be told when something about this document's subject changes upstream (a renewal page, a portal), offer the `watch` skill in one line — do not start it unasked.

## 6. Sub-commands

- `add-source --replace <id> <new-file>` — replace a document's content. The old
  file is renamed `<oldname>-superseded-<YYYY-MM-DD>.<ext>` next to it (history
  preserved; its `.meta.md` sidecar is renamed alongside); the new file takes the
  original name; the index row is updated via `sources_index refresh`.
- `add-source --untag <id> --from-domain <id>` — remove the row from the
  domain's `sources.md`. The row is moved to `## Removed (history)` at the
  bottom of that file. The document itself stays in `Sources/`.
- `add-source --untag <id> --from-project <id>` — same for projects.
- `add-source --move <id> --to-path <new-workspace-relative-path>` — `mv` the
  document (and its sidecar) under `Sources/` and update the index. Use this when
  re-organizing the layout; the index id is regenerated from the new path.
