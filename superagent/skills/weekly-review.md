# Superagent weekly-review skill

> **Bulk reads** (`rules/subagents.md`): any lookup expected to pull more than
> ~20k tokens of raw tool results (~10k once the economy level resolves to `full`;
> multi-entity sweeps, whole email thread trees, long histories or archives) runs
> in a subagent (`Explore` read-only / `general-purpose` if it must write) that
> returns only the synthesis — named facts, quotes, `file:line` pointers — never
> raw dumps into the main transcript.


Compute a **trailing 7-day window** ending today (local).

## 1. Check the weekly watchlist cycle

Per `contracts/watchlist.md`:

```bash
uv run python -m superagent.tools.watchlist check --cycle weekly-review --report
```

No `Sources/Watchlist/` folder = skip silently. Cycles nest (`contracts/watchlist.md` § 2): this one run covers the weekly watchers (`cycles` include `weekly-review` / `schedule: weekly`) **and every daily watcher**, so the review never needs `daily-update` run first; each watcher's own throttle keeps a same-day double check from re-fetching. Dispatch any `dispatch[]` specs as read-only subagents and `stamp` each outcome (same procedure as `daily-update` § 3). Fold the `--report` markdown into the review under **Alerts**.

`simplefin` (pack defaults `cycles: [daily-update]`, `schedule: daily`, `capture_mode: automatic`) is therefore covered by this check too: if the daily run already pulled today, the budget gate (≤ 24 calls/day, 60 min apart) makes this a no-op; otherwise `check` harvests it now and the rows are in `_memory/transactions.yaml` before the bookkeeper pass. A `budget_exceeded` result is reported, never retried. A `simplefin` row the user pinned to `capture_mode: manual` is never dispatched by `check` — it arrives as a `kind: harvest` dispatch spec; ask once —

> "The bank / brokerage feed has not been pulled since <date>. Pull it now? (yes / skip)"

— and on yes run the on-demand harvest (the run row lands in `ingestion-log.yaml`):

```bash
uv run python -m superagent.tools.watchlist harvest --id simplefin
```

Collect counts.

## 2. Bookkeeper pass

If finance data is flowing — the `simplefin` harvest or a `csv.py --file` import has landed rows in `_memory/transactions.yaml`:

1. Read transactions from `_memory/transactions.yaml` (the `simplefin` harvest and CSV imports both write here).
2. Run the reconciler for a 7-day window — it cross-references transactions against `bills.yaml` (matched / missed) and surfaces recurring-charge candidates not yet tracked in `bills.yaml` / `subscriptions.yaml`:

   ```bash
   uv run python -m superagent.tools.reconcile_transactions --days 7
   # or `--json` for structured consumption
   ```

3. Surface in the review under headings: **Bills missed**, **Bills paid**, **Recurring-charge candidates** (audit prompt: "Add to bills.yaml or subscriptions.yaml?").
4. Independent of the reconciler, total `inflows` and `outflows` for the trailing 7 days; group outflows by `category`; flag categories > 1.5× their 4-week trailing average. When totalling, skip rows flagged `stale_pending: true` or carrying `superseded_by` — they are pending twins of a posted transaction and would double-count.

If no finance data is flowing, skip with a one-line note: *"Bookkeeper pass skipped — no finance watcher configured. See `docs/data-sources.md#simplefin` (or import a CSV) to enable."*

## 3. Coach pass

If health / fitness data is flowing into `health-records.yaml` (a wearable watcher or manual `health-log` rows):

1. Workouts logged this week (count + total minutes + total distance if applicable).
2. Sleep average (hours, score) over last 7 nights.
3. Weight trend (delta vs 4 weeks ago).
4. Personal-signal events captured this week (count by category).
5. Streak status against any active goal in `Domains/Hobbies/status.md`.

If no fitness data is flowing, surface manual reflection prompt:

> "Coach pass: no fitness source configured. Want to log this week's workouts manually? (`Hobbies` domain)"

## 4b. Project rollup

Read `_memory/projects-index.yaml.projects[]`:

For each project with `status: active`:
- **Burn-down**: render `{checked}/{total} success criteria — {days} days to target` (when criteria ≥ 5).
- **This week's progress**: count of tasks completed for this project in last 7 days; H4 entries appended to project's `history.md` in last 7 days.
- **Stalled?**: if NO entry in the project's `history.md` AND no completed tasks in last 14 days → flag as `stalled`. Suggest pause or push.
- **Drift**: index-status-vs-activity mismatches (e.g. `active` in the index but a silent history) are flagged per doctor's project-drift check — cite it, don't re-derive here.

Also list:
- **Projects in `planning`** — chartered but not yet active. Prompt: "ready to flip these to active?".
- **Projects with target_date in next 30 days** — will dominate the next monthly cycle.
- **Recently completed projects** (last 7 days) — surface lessons-learned prompt if not already captured.

## 5c. Stale Outbox drafts

Per `contracts/outbox-lifecycle.md` § "Stale-drafts surfacing". Read
`config.preferences.outbox.drafts_stale_days` (default **14** when the key is
absent), then tail-read `_memory/outbox-log.yaml.artifacts[]` (time-shape):

- Keep rows with `stage: drafts` whose `last_updated` (fall back to the newest
  `stage_history[].ts`) is older than `drafts_stale_days`.
- For each, check that `path` still exists on disk. Existing → list as
  `<path> — drafts since <date> (<N> days)`. Missing → list separately as an
  **untracked deletion** and offer to mark the row `stage: discarded`.

Skip the section silently when nothing qualifies (or the log is absent).

## 7. Reflection prompt

Ask the user (one prompt, accept skip):

> "Two questions for the log — type a sentence each, or 'skip':
>
>   1. **What worked well this week?**
>   2. **What do you want to do differently next week?**"

Capture both answers as a single H4 entry in `Domains/Self/history.md`:

```markdown
#### <YYYY-MM-DD> — Weekly review

**Worked well**: <answer 1>

**Differently next week**: <answer 2>

---
```

If either answer hints at a personal signal (heuristic: contains words like "should", "need to", "want to be", "next time"), capture as a `personal-signals.yaml` row (per `contracts/capture.md` § 7.1) and tag it inline.
