# Superagent refresh — update the framework from git

The user-facing entry point for updating an existing Superagent
installation. One run performs the full update sequence: **fetch → show
what's new → confirm → fast-forward pull → re-sync environment → migrate
workspace data** (via the `migrate` skill).

User priorities, in order:

1. **Never lose the user's work.** `workspace/` is gitignored and untouched
   by design; local framework modifications are surfaced and preserved
   (stash or abort), never discarded. No destructive git commands
   (`reset --hard`, `checkout -- .`, `clean`) without an explicit per-run
   user choice.
2. **Leave the installation consistent.** Framework code, `uv.lock`
   environment, git hooks, and `workspace/.version` all end the run in
   agreement — or the run halts with a clear statement of the exact
   intermediate state.
3. **Show before pulling.** The what's-new delta and migration implications
   are presented before anything changes.

This skill **never pushes**, never commits, and never edits framework
files — it only moves the checkout forward and runs the documented
post-update steps.

## 1. Preflight

1. Read `workspace/_memory/config.yaml`. If it does not exist this is a
   fresh checkout, not an update — point the user at the `init` skill and
   exit.
2. Resolve the default branch: `git symbolic-ref --short
   refs/remotes/origin/HEAD` (strip the `origin/` prefix; fall back to
   `master` if unset). Call it `<default>` below.
3. Record the starting state (batch these in ONE parallel tool-call
   message):
   - `uv run python -m superagent.tools.version current` → `<old_version>`
   - `uv run python -m superagent.tools.version workspace` → `<ws_version>`
   - `git rev-parse --abbrev-ref HEAD` → current branch
   - `git status --porcelain` → local modifications
4. **Branch check.** The supported update path is `<default>`. If HEAD is
   detached or on another branch, tell the user which ref they are on and
   ask (`AskQuestion`): `switch to <default> and update` / `cancel`. Never
   force-switch silently.
5. **Dirty-tree check.** `workspace/` and `tasks/` are gitignored, so
   anything `git status --porcelain` reports is a *framework* modification.
   If the tree is dirty, list the files and ask (`AskQuestion`):
   - `stash and continue` — record the choice; the actual `git stash push`
     runs in step 4.1, immediately before the pull, so every earlier exit
     path (nothing to pull, cancel, diverged history) leaves the working
     tree untouched.
   - `cancel` — exit without changes; suggest committing or reverting the
     local edits first.

## 2. Fetch and compare

1. `git fetch origin --tags --prune`.
2. `git rev-list --count HEAD..origin/<default>` → `<behind>` and
   `git rev-list --count origin/<default>..HEAD` → `<ahead>`.
3. Resolve the incoming framework version:
   `git show origin/<default>:pyproject.toml`, read `[project].version`
   → `<new_version>`.
4. Route:
   - `<behind> == 0` — framework already newest. Report `Framework already
     at <old_version> — nothing to pull.` Then still run
     `uv run python -m superagent.tools.version check`: if the *workspace*
     lags the framework (a previous pull without migration, exit code 1),
     jump to step 6; otherwise exit.
   - `<ahead> > 0` — the user has local commits the remote doesn't have. A
     fast-forward is impossible; do **not** rebase or merge autonomously.
     Report the situation (`<ahead>` local commit(s) on top of
     `origin/<default>`), suggest the user reconcile (push, rebase, or
     branch off), and exit. This is the expected state on the framework
     *author's* machine — `refresh` is for consumers.
   - `<behind> > 0`, `<ahead> == 0` — continue to step 3.

## 3. Show what's new + confirm

1. Build the delta, cheapest sources first:
   - **Roadmap "Released" table**: `git show
     origin/<default>:superagent/docs/roadmap.md`, take the version rows
     between `<new_version>` (inclusive) and `<old_version>` (exclusive).
     This is the primary user-facing changelog.
   - Supplement with `git log --oneline HEAD..origin/<default> | head -20`
     when the roadmap rows are sparse.
2. Preview the migration impact **without changing anything yet**: from
   `git show origin/<default>:superagent/migrations/_manifest.yaml`, list
   the migration entries with `to_version` in `(<ws_version>,
   <new_version>]` and flag any marked `breaking: true` or
   `revertible: false`.
3. Print the plan:

   ```
   Superagent update available: <old_version> to <new_version> (<behind> commits)

   What's new:
     - <version>: <roadmap summary, one line per release>

   Workspace migrations that will follow the pull: <N> (via migrate)
     [flag any breaking / non-revertible steps here]
   ```

4. `AskQuestion` (single gate): `update now` / `show full changelog first` /
   `cancel`. On `show full changelog first`, print the full
   `git log HEAD..origin/<default>` subjects, then re-ask.

## 4. Update the checkout

1. If the user chose `stash and continue` in step 1.5:
   `git stash push -m "superagent-refresh <date>"`.
2. `git pull --ff-only origin <default>`. The `--ff-only` flag is
   non-negotiable — if it fails, halt and report (see Failure handling);
   never fall back to a merge or rebase autonomously. If step 4.1 pushed a
   stash, pop it before exiting on this failure.
3. If step 4.1 pushed a stash, `git stash pop` now. On conflict, leave the
   stash intact, report the conflicting files, and continue (the update
   itself succeeded; the user resolves the stash at leisure).
4. Confirm landing: `uv run python -m superagent.tools.version current`
   must print `<new_version>`.

## 5. Post-update environment sync

Run the documented post-pull steps (batch 1 and 2 in parallel):

1. **Dependencies** — `uv sync` so `.venv` matches the pulled `uv.lock` /
   `pyproject.toml` (`rules/development-tooling.md` § 1).
2. **Git hooks** — `git config core.hooksPath .githooks` (idempotent;
   re-asserts the pre-commit + commit-msg hooks).
3. If `uv sync` fails, halt here and report — the framework code is updated
   but the venv is stale, and skills that shell out to tools may misbehave
   until `uv sync` succeeds.

## 6. Migrate workspace data

Run `uv run python -m superagent.tools.version check`:

- exit `0` — workspace already matches; continue to step 7.
- exit `1` — **dispatch into the `migrate` skill** and let it carry this
  leg: it owns the PATCH-only silent bump, the chain plan, the confirm
  gate, per-step validation, and interaction-log rows. Do not reimplement
  any of that here.
- exit `2` — downgrade scenario; should be impossible immediately after a
  pull to newest. If it happens, dispatch into `migrate` (its downgrade
  handling applies) and flag the anomaly to the user.

If the user cancels the migration inside `migrate`, do not undo the pull —
report that the framework is at `<new_version>` while the workspace remains
at `<ws_version>`, and that data-write skills may misbehave until the
migration runs (same soft warning as `AGENTS.md` § "On workspace open").

## 7. Final summary + log

1. Report one consolidated block:

   ```
   Superagent updated: <old_version> to <new_version> (<behind> commits pulled)
     deps: uv sync OK        hooks: .githooks OK
     workspace: <ws_version> to <final_ws_version> (<N> migration step(s))
     [stash: popped cleanly | left in stash due to conflicts in <files>]
   ```

2. Append one row to `workspace/_memory/interaction-log.yaml` per its
   schema (`skill: "refresh"`, `action: "framework-update"`, summary noting
   commits pulled, sync results, and the workspace version transition).
3. End with a stray-file sweep: `git status --short` must be clean (or show
   only the pre-existing stash-pop conflicts reported in step 4.3).

Skill done.

## Failure handling

- **`git fetch` fails** (no network, SSH auth) — nothing has changed;
  report the exact error and the remote URL (`git remote get-url origin`)
  and exit.
- **`git pull --ff-only` refuses** — the tree diverged between steps 2 and
  4 (or an ahead-count edge case). Nothing merged; report and exit with the
  `<ahead>` / `<behind>` counts.
- **`uv sync` fails** — code updated, venv stale. Report the error
  verbatim; suggest re-running `uv sync` after fixing. Do not proceed to
  migrations — migration helper scripts run through the venv.
- **Migration fails** — the `migrate` skill owns the halt semantics (the
  workspace stays at the highest successfully-migrated version). Never roll
  back the git pull in response.

## Guardrails

- **Consumer-side only.** Never commit, push, tag, or edit framework files.
- **`--ff-only`, always.** No autonomous merges or rebases.
- **No destructive git** without an explicit same-run user choice; the only
  mutation offered is a named `git stash`.
- **`workspace/` data is out of scope** except through the `migrate`
  dispatch. This skill never edits memory YAML, domain files, or `_custom/`
  overlays.
- **Ask once.** One confirmation gate (step 3.4); the environment-sync and
  logging steps run unprompted after the user approves the update.
