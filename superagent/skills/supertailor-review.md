# Superagent supertailor-review skill

> **Bulk reads** (`rules/subagents.md`): any lookup expected to pull more than
> ~20k tokens of raw tool results (~10k once the economy level resolves to `full`;
> multi-entity sweeps, whole email thread trees, long histories or archives) runs
> in a subagent (`Explore` read-only / `general-purpose` if it must write) that
> returns only the synthesis — named facts, quotes, `file:line` pointers — never
> raw dumps into the main transcript.


**Supertailor is the name of this review. It is a skill, and no agent of its own.** The lead agent runs it every 90 days or on request (duty `supertailor-review` in `agents/superagent.agent.md`). The review does three things:

1. **Observes** — reads the interaction log (`signals log-show`), the prompt log (`log_user_query --show`), `_memory/personal-signals.yaml`, `_memory/action-signals.yaml`, agent transcripts and the workspace folder structure, to learn how the framework is actually used: which skills fire often and which never, which capture rules trip and never get drained, which domains are tended and which are stagnant, where the user keeps asking the same question (surfacing is broken) or keeps correcting the model (a rule is missing).
2. **Proposes** — writes ranked, evidenced suggestions for framework improvements to `_memory/supertailor-suggestions.yaml`.
3. **Routes** — tags every suggestion with a `destination` (`superagent`: generic, goes into the committed framework; `_custom`: user-specific, goes into `workspace/_custom/`) and with the `agent` it concerns. The dev twin of that agent builds an approved suggestion under `rules/framework-changes.md`.

**The review writes no implementation code** (§ "Boundaries" at the end of this file).

## 1. Hygiene pass

Mark the run as started (the attempted marker, so a review that stops midway stays visible to `cadence status`): `uv run python -m superagent.tools.cadence start supertailor-review`.

Mechanical, reversible checks that keep the workspace tidy:

1. **Template compliance**: every `Domains/<domain>/` has the four files (`info.md`, `status.md`, `history.md`, `rolodex.md`); every `info.md` carries the maintenance banner; every `history.md` has the right `## Log` shape with H4 date headers; every `status.md` has `## Status / ## Open / ## Done` blocks.
2. **Orphan detection**: folders under `Domains/` with no `domains-index.yaml` row; index rows that point to a folder that does not exist; assets in `assets-index.yaml` that name a domain that does not exist; contacts cited in a `rolodex.md` that are missing from `contacts.yaml`.
3. **Memory staleness**: `context.yaml.last_check` older than 7 days; `model-context.yaml` not updated this month; `daily-update` last ran more than 7 days ago; `weekly-review` more than 14 days ago; `monthly-review` more than 45 days ago.
4. **Cadence adherence**: surface "you said weekly review weekly but the last one was 23 days ago — drop the cadence preference, or is something off?". `uv run python -m superagent.tools.agents duties --overdue` lists every late duty with the agent it belongs to.
5. **Schema integrity**: validate every `_memory/*.yaml` against its `schema_version` (delegate to `tools/validate.py`); flag any row with required fields missing.
6. **Watchlist health**: every `_memory/watchlist-state.yaml` row with `error_streak > 0` or `status: evicted` surfaced with its `last_error` / `evict_reason` and one-line "what to fix" (per `contracts/watchlist.md`). Also every **healthy watcher overdue against its schedule**: `uv run python -m superagent.tools.cadence status --json` → `overdue_watchers` (active, `error_streak: 0`, last success older than its fastest cycle's period plus one day). It is not broken — the cadence that runs it has lapsed — so the fix to name is that cadence (`daily-update` / `weekly-review` / `monthly-review`).
7. **Custom-overlay scaffold**: ensure `_custom/{rules,skills,agents,templates,tools,watchers}/` exist; offer to create the empty folders when one is missing.
8. **Improvement-ideas catalogues exist**: verify the two hand-curated idea catalogues named in `agents/superagent.agent.md` § "Framework review and framework changes" are present and parseable, with the tier headings that section lists. They are mandatory inputs to step 3 below; a missing file silently degrades the review. Surface as `needs-attention` (not auto-fixable — both are hand-curated).
9. **Signal-capture health**: near-zero rows in `action-signals.yaml` + `personal-signals.yaml` while the prompt log is dense over the same period → capture-adherence failure (the session-end sweep in `contracts/capture.md` § 7.2a is not running); surface as `needs-attention`.
10. **Memory-routing check**: run `uv run python -m superagent.tools.memory_routing_check --since <last review>`; exit 1 → flag the reported files for migration per `rules/memory-routing.md`.
11. **World-graph consistency**: run `uv run python -m superagent.tools.world validate` (per `contracts/world-graph.md` § 5); exit 1 → list the dangling edges as `needs-attention` with the one-line fix `uv run python -m superagent.tools.world rebuild` (the graph is derived; a rebuild is always safe).
12. **Agent roster**: run `uv run python -m superagent.tools.build_agent_manifest --check` and `uv run python -m superagent.tools.agents list`; a role file with a problem, a role without its dev twin, a stale manifest or a registry row with no role file is surfaced as `needs-attention` for the dev twin of that agent (`contracts/agents.md`).

For each finding, list it; ask `approve all / approve some / decline all`.

- **A repair to a workspace file** (a missing banner, a broken pointer in a `sources.md`, an empty overlay folder) is mechanical and reversible: the session running the review applies the approved ones itself, one edit per repair, and logs them. The file-by-file safety nets in `superagent/docs/faq.md` are the rollback path. A repair that would lose information is never mechanical: file it as a strategic suggestion instead.
- **A repair to a framework file** (under `superagent/`) is never applied by the review. It becomes a suggestion with `destination: superagent`, and a dev twin builds it (step 6); `git revert` is its rollback path.

## 2. Strategic pass

Pattern detection on usage data, to surface friction and capability gaps:

1. **Friction patterns** from the prompt log (`uv run python -m superagent.tools.log_user_query --show` `--since <last review> --no-synthetic`: one merged view of every machine's file; clusters of similar queries the user keeps asking are candidates for a new skill or a new surfacing rule; skip rows tagged `synthetic: true` — harness-generated turns, not the user) and the open `target: tailor` signals (`uv run python -m superagent.tools.signals list --open --target tailor`; open = `status` not in {`processed`, `declined`}; kinds frustration, wish, correction).
2. **Skill utilization** — skills not run in 30 days: either the user does not need them (deprecation candidates) or does not know about them (a discovery nudge in the relevant cadence skill). Skills run with high frequency are optimization candidates.
3. **Domain utilization** — domains with no `history.md` entry in 12 months (archive candidates) and domains with more than 50 entries a month (split candidates).
4. **Ingestor utilization** — sources that ingest regularly but whose data is never queried (candidates for `capture_mode: manual` or disabling) and sources that are not configured but whose data the user keeps asking about (recommend setup: "You ask about your weekly mileage often. Want to set up a fitness watcher?").
5. **Auto-capture rule misses** — a personal signal or action signal added by hand within an hour of an ingest run is a candidate auto-capture rule the framework missed.
6. **Output / template critiques** from `action-signals.yaml` rows with `kind: artifact-critique`: the user pointed at a generated artifact and said it was broken. Propose the template or skill change that fixes the class of issue.
7. **Agent change requests** — open `target: tailor` signals filed by a running agent about its own role, duties or checks. Each becomes a suggestion for that agent's dev twin.

Each strategic finding becomes a row in `_memory/supertailor-suggestions.yaml` with full context (problem, evidence, suggestion, implementation_sketch, effort, risk, destination, agent). The row shape is in § "Suggestion row" below.

## 3. Consult the improvement-ideas catalogues

Before drafting any new suggestion, the review MUST check whether the friction patterns from step 2 match a pre-analyzed entry in one of the two hand-curated idea catalogues that `agents/superagent.agent.md` names under "Framework review and framework changes" — one of structural-improvement options, one of token-efficiency / cache / latency improvements. This avoids re-deriving ideas the framework has already thought through, and surfaces "this isn't a one-off; it's been catalogued since <date>".

### 3a. Read the catalogues

Use a TOC-first read pattern: read each catalogue's section index, then jump only to the relevant tier sections. Do not load whole catalogues into context.

### 3b. Match friction → catalogue entry, then check for a prior retirement

For each friction theme from step 2, check whether a catalogue entry addresses it. Typical pairings: repeated "what changed since I last looked" → differential snapshots; repeated "find that note about X" → full-text search / embeddings; "where did this fact come from?" → provenance; slow or expensive sessions → the perf catalogue's quick-wins tier.

Several catalogued entries were shipped and later pruned for zero usage — `docs/roadmap.md` § Released lists every retired artifact by name in each prune release's row (0.8.0 onward). Before citing any catalogue match, check the Released table for a prior retirement; if found, the suggestion MUST cite the prune in `evidence` and show fresh usage signal before re-proposing — never re-propose a pruned feature on the catalogue entry alone.

### 3c. Cite the match in the suggestion

When a friction theme matches a catalogue entry, the resulting `supertailor-suggestions.yaml` row MUST cite it:

- `evidence`: append `" — matches catalogue: <catalogue short name> § <entry id> (<entry title>)"`.
- `implementation_sketch`: prefer pointing at the catalogue's existing sketch over re-deriving it.

### 3d. Surface gaps

If a friction theme matches NO catalogue entry, note it in the report under `### Catalogue gaps` with a one-line description. Do NOT auto-add to the catalogue (it's hand-curated). The user can promote during the review or ignore.

### 3e. Do not mutate the catalogues

The catalogues are READ-ONLY for the review. New ideas surfaced here go into `supertailor-suggestions.yaml` as normal; promoting them into the catalogue is a manual user step.

## 4. Destination and agent classification

For every suggestion, before it is written:

1. **Destination.** `superagent` — a generic improvement that benefits any user: a skill anyone could use, a watcher pack for a popular source, a fix to a briefing's format, a universally useful auto-capture rule, a template, a doc fix. `_custom` — an improvement that names the user's own assets, contacts, accounts, addresses, household routines or preferences: a skill that drafts one family's carpool email, a template styled for one tax preparer, a household-specific reminder rule. **Default to `_custom` whenever unsure.**
2. **Token-scan safeguard** — before a suggestion is written with `destination: superagent`, scan its body (problem + evidence + suggestion + implementation_sketch) against:
   - `_memory/contacts.yaml.contacts[].name` and `.aliases[]`
   - `_memory/domains-index.yaml.<domain>.id`
   - `_memory/assets-index.yaml.<asset>.name` and `.serial`
   - `_memory/accounts-index.yaml.<acct>.name`
   - Address-fragment / license-plate / account-number regex patterns from those same files
3. On any match, force `destination: _custom`. Add `implementation_notes: "Auto-routed to _custom/ — safeguard matched: <token>"`, and say in the report that the route changed and why. This is the single most important safety guarantee: personal data cannot leak into committed framework code, even when the user asks for that route. The dev twin runs the same scan again at the write (`rules/framework-changes.md` § 2), so a classification mistake here cannot leak either.
4. **Agent.** Name the agent the suggestion concerns in the row's `agent` field: the role whose role file, duties, checks or skills the change touches (`uv run python -m superagent.tools.agents list` shows the roles). A change to the watchlist or a harvest concerns the role with the `watch` duty; a change to bills, subscriptions or spending concerns the role that owns those stores; a change to the generic project role concerns `project`. Everything else, and anything in doubt, concerns the lead. That agent's dev twin builds the suggestion.

The destination decides the **target path** and whether the safeguard applies. The agent decides **which dev twin** builds it.

## 6. Hand-off

An approved suggestion is built by **the dev twin of the agent it names** (`agent` field; the lead when the field is empty), under `rules/framework-changes.md`. The review itself never implements.

1. `uv run python -m superagent.tools.agents id <agent> --dev` prints that dev twin's id.
2. **No separate agents running (the default).** The chat session takes the dev role: read `agents/<agent>.agent.dev.md` and `rules/framework-changes.md` (for a custom role, the files under `workspace/_custom/agents/`), then build the suggestion. Prefer a fresh session for it when the review session is already long.
3. **The dev twin runs as its own agent.** Send it the suggestion id and nothing else; it reads the row itself.
4. The dev twin re-runs the safeguard (`destination: superagent`), implements, tests, and either commits (`superagent/`) or writes into `workspace/_custom/` (nothing to commit: `workspace/` is gitignored). It then sets the row to `status: implemented` with `implementation_notes` carrying the commit SHA or the file path, and tells the running agent to pick the change up when a role, duty or check changed.

## 7. Update memory

1. `uv run python -m superagent.tools.cadence finish supertailor-review` (stamps `last_runs.tailor_review`, clears the started marker).
2. Log through `signals log`.
3. `supertailor-suggestions.yaml` updated with the new rows.
4. Close every signal this run consumed: `uv run python -m superagent.tools.signals close <id> --became-suggestion <st-id>` when it fed a suggestion, `--became-action "<label>"` when a hygiene repair or workspace action resolved it, `--declined "<reason>"` when it needs no change. A consumed signal left open pads the next run's backlog and every cadence counter.
5. (Designed, not yet shipped: `_memory/_checkpoints/<date>/` populated with backups of any files modified by hygiene-pass repairs — blocked on `roadmap.md` § S-27.)

## Suggestion lifecycle

1. **Proposed** — the review adds the row with `status: proposed`. The next review summary surfaces it.
2. **Approved** — the user picks "approve". `status: approved`, `resolved_at: <now>`. The suggestion goes to the dev twin of its agent (step 6), whatever its destination.
3. **Declined** — the user picks "decline". `status: declined`, `resolved_at: <now>`, the reason in `notes`. A declined suggestion is never re-proposed (matched by `problem` text similarity) without a clear new piece of evidence.
4. **Implemented** — once the dev twin wrote the change, `status: implemented` and `implementation_notes` records what was created or modified plus the commit SHA.
5. **Deferred** — the user picks "defer" or "later". The row stays `status: proposed` and `notes` records "deferred from <date>". It does not re-surface in the next 14 days. A dev twin's safeguard refusal also sets `status: deferred` (step 5 surfaces it first).

## When the review runs

- On request: the triggers in this file's frontmatter.
- As the lead's duty, every 90 days (`config.preferences.cadences.tailor_review`); `cadence status` names it when it is late.
- `daily-update` / `weekly-review` nudge a run when: more than 90 days passed since the last review AND `_memory/action-signals.yaml` has unprocessed `target: tailor` rows; a deferred suggestion's window has expired; or the hygiene pass would produce more than 5 mechanical repairs (a sign of drift).

## Boundaries

- **The review writes no implementation code.** Nothing under `superagent/`, nothing under `workspace/_custom/`. Its own writes are `_memory/supertailor-suggestions.yaml`, the report, and the approved mechanical repairs to workspace files from step 1.
- It does not write to `workspace/Domains/` narrative, `_memory/bills.yaml`, `_memory/health-records.yaml` or any other store an operational skill owns, beyond those approved mechanical repairs.
- Hygiene repairs are mechanical and reversible only. Anything that would lose information needs the user's approval and goes in as a strategic suggestion.
- Observing and building stay apart on purpose: the review proposes, the user approves, a dev twin builds. Folding them together would turn every observation into an inline "shall I fix it?" and remove the second run of the safeguard.
