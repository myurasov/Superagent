# Superagent start skill

In Autocode mode each agent runs as a session of its own, registered with an Autocode server, and its duties run from wakes (`contracts/agents.md` § 9, `rules/autocode.md`). This skill is the way in and the way out. Three rules hold in every step:

- **Ask in cards, write with the tool.** Never ask the owner to edit a file or to run a command. Every write below is a command this session runs.
- **Nothing starts without the owner's yes in this session.** A run with nobody present never runs this skill.
- **What is recorded is what the owner saw.** A changed term is a new question.

A harness without a question tool asks the same questions in prose and waits for the answer.

## 1. Read the state

```bash
uv run python -m superagent.tools.autocode setup     # --json for the data; it writes nothing
```

Its first three lines decide the path:

- **`Autocode: not installed ...`** or **`... does not run its plugin`**: Autocode mode cannot be started from this session (it needs OpenCode with the Autocode plugin). Say so in one line, say that Superagent keeps working in this chat as before, and stop.
- **`Mode: OFF`** → § 2. **`Mode: ON. Not set up yet.`** → § 3. **`Mode: ON. Set up.`** → § 3, in its shorter form.
- **`This session: registered as <id>`** with an id that is not the lead's: this session is another agent (a dev twin, another role) and keeps its id. The lead is then started in the background in § 6, like the others; skip § 5.
- The owner asked to stop → § 8. The owner asked to change a setting → § 3 (`Change`), § 4, then § 7 "After a change".

## 2. The switch (asked while the mode is off)

One question: **"Run Superagent's agents in the background (Autocode mode)? They work on a schedule without you, and each run uses the model."** Options: `Turn it on` / `Not now`.

- `Turn it on`:

  ```bash
  uv run python -m superagent.tools.autocode setup enable
  ```

- `Not now`: stop. The chat session keeps taking every role, and "start superagent" asks again at any time.

## 3. Settings and agents (one card)

Show the `Settings:` and `Agents:` blocks of § 1 as a short table: each agent with its wakes, and each wake's time in plain words beside its trigger ("every day at 08:30", "Sundays at 18:00", "every 30 minutes, when something is due"). Then the work hours of the scheduled update (the proposed value where none is set), the daily cost cap per agent, and the model of agents started in the background. Add two lines: a wake runs its check first, so a run with nothing due costs nothing; what a real run costs shows in the first days.

Then one card with two questions.

1. **The settings.**
   - First start (`Not set up yet`): `Approve` (the schedule, work hours and cap as shown) / `Change` / `Start idle` (no schedule: the agents wake on a message only) / `Cancel`.
   - Later start (`Set up`): `Start with these` / `Change` / `Cancel`.
2. **Which other agents start with the lead** (several may be picked): one option per agent of the list that is not the lead, the one tagged `recommended` first, as `<name> (Recommended)`. Leave out an agent whose row is already `active` or `dormant`, and name it as running.

On `Change`, ask what to change, in plain words or in a follow-up card: a wake's time, a wake to leave out, the work hours, the daily cap, the model of the background agents. Then show the changed table and get a yes to it. On `Cancel`, stop: nothing was written beyond the switch.

## 4. Record what was approved

```bash
uv run python -m superagent.tools.autocode setup apply --approval "<the owner's words>" --agents <a,b> \
  [--work-hours "06:00-23:00"|none] [--daily-usd <N>|none] [--wake '<agent>:<wake>=<trigger>'] \
  [--skip <agent>:<wake>] [--no-wakes] [--runner-model <provider/model>] [--runner-variant <variant>]
```

- `--approval` is what the owner answered, with the changes they named ("Approve; daily briefing at 07:00"). It is written on every grant.
- `--agents` lists the agents picked in question 2; the lead is always part of it.
- `Approve` with a proposed work-hours value: pass that value in `--work-hours`. `Start idle`: `--no-wakes`. `Start with these` and nothing changed: run it as is; it then reports that nothing changes.
- After a `Change`, run it with `--dry-run` first and show its lines as the final terms.
- The tool refuses a scheduled update that lies outside the work hours, since a held update never runs. Tell the owner, offer the two fixes (another time, other hours), and ask again.

The command writes the settings into `_memory/config.yaml` (one line each, comments kept), a registry row per agent, and a grant per wake (`contracts/agents.md` § 8). It starts nothing.

## 5. Become the lead (this session)

Skip this section when this session is registered as another agent (§ 1).

1. `uv run python -m superagent.tools.autocode prompt <lead>` prints the lead's start steps. Do its steps 1 to 4 here: register under exactly the id it names (the Autocode tool `autocode_me`, action `register`), read `rules/autocode.md` and the role file, and set each wake it lists with exactly that name, trigger, check and text (`autocode_wake`, action `set`). Skip its last two steps: the owner is here.
2. Mark the row:

   ```bash
   uv run python -m superagent.tools.autocode mark <lead>
   ```

- **`id_taken`**: another session holds the lead's id. Never register under another id. Say so, and go on with § 6: the other agents can still start. Moving or removing an id is done in Autocode itself, by the owner.
- **This session already is the lead**: set the wakes again (the same terms change nothing) and run `mark`.

## 6. Start the other agents

One after another, each with a long time limit (a start returns when the new agent finished its first turn, which takes a few minutes):

```bash
uv run python -m superagent.tools.autocode start <agent>
```

It opens a session in this checkout with the model of the agent's tier and gives it the start prompt (register under its id, read the rule and its role file, set its granted wakes and no other), then marks its row and its host. When a start fails, name the agent, show the tool's line, and go on with the rest. Never retry in a loop.

## 7. Confirm and tell

1. List what is registered: the Autocode tool `autocode_me`, action `discover`, pattern `<prefix>:*`.
2. Report in one table: each agent, its state, its wakes. Then three lines: the briefings arrive in this session and as a report; "stop superagent" stops everything; "change the agents' schedule" changes a time.
3. From here on this session is the lead as a registered agent, and `rules/autocode.md` holds for it.

**After a change** of settings while agents run (§ 3 `Change`, § 4): set this session's wakes again from `autocode prompt <lead>`, and send each other running agent one message, `Pick up: your wakes changed`, so it sets its own again.

## 8. Stop ("stop superagent", "turn Autocode mode off")

1. One question: `Stop all agents` / the agents by name (several may be picked) / `Cancel`.
2. Each background agent:

   ```bash
   uv run python -m superagent.tools.autocode stop <agent>
   ```

   It asks the agent to cancel its wakes and unregister, then marks its row `off`.
3. This session, when it is the lead and was picked: cancel its own wakes (`autocode_wake`, action `cancel`, each one), unregister (`autocode_me`, action `unregister`), then `uv run python -m superagent.tools.autocode mark <lead> --off`.
4. When every agent is stopped, offer to turn the mode off, and on a yes run `uv run python -m superagent.tools.autocode setup disable`. The grants stay recorded, so the next "start superagent" proposes the same settings.
